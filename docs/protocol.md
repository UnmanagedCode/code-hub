# Protocol: `.hub.json` manifest + HTTP API

## `.hub.json` (project root)

| Field | Type | Required | Meaning |
|---|---|---|---|
| `start` | string | **yes** | Blocking foreground command. Must bind `$PORT` and stay up until killed. Run via `bash -lc` in its own process group with `env.PORT` set to the app's port: the app's Settings `port`, else the manifest's `port`, on a non-worktree checkout, otherwise an allocated free port. |
| `name` | string | no | Display name (default: directory basename). |
| `healthPath` | string | no | HTTP path polled for readiness; any HTTP response = ready. |
| `readyWhen` | string | no | Regex matched against the child's stdout/stderr to detect readiness. Matched in bounded windows under a time limit; see "`readyWhen` matching" below. |
| `port` | integer | no | Fixed port for the **default checkout**; `1024`–`65535`. When absent, a free ephemeral port is allocated on every start. Worktrees always get a free port and never inherit this. An app's Settings `port` overrides it. An app's Settings `port` overrides it. A busy fixed port **refuses the start** (`409`) rather than falling back — a port that quietly moves defeats the point of pinning it. |
| `routes` | array | no | Named URLs the app serves. Non-empty array of `{ name, path }`; `name` a non-empty string, `path` a string starting with `/`. When absent, a single implicit route at `/` is used. |

Readiness precedence: `readyWhen` → `healthPath` → default TCP connect probe on `$PORT`. 30s timeout; on timeout the app stays running, flagged readiness-unconfirmed. Validation rejects missing/empty `start`, non-string optionals, a `routes` value that isn't a non-empty array, any route entry missing `name` or with a `path` not starting with `/`, a `port` that isn't an integer in `1024`–`65535` (`"port" must be an integer between 1024 and 65535 (got 80)`), and a `readyWhen` that is not a valid regex or nests a repeating quantifier (`"readyWhen" nests a repeating quantifier inside a repeated group ("(a+)+"), …`) — loudly, naming the offending file (e.g. `routes[1].path is required and must start with "/"`). Rejecting a bad `port` at validation time means it surfaces as a `manifestError`/`400`, never as an opaque child crash. A broken manifest surfaces as a non-startable app (with `manifestError`), not a hidden one.

**`readyWhen` matching** (constants in `src/readyWhen.js`):
- Each poll tick tests only output that arrived since the last tick plus `READY_OVERLAP_CHARS` of tail, cut into slices of at most `READY_WINDOW_CHARS`; consecutive slices overlap by `READY_OVERLAP_CHARS`.
- A match whose text is at most `READY_OVERLAP_CHARS` long is always found, including one split across two output chunks. A match longer than `READY_WINDOW_CHARS` is never found; in between is not guaranteed.
- `^` and `$` (no `m` flag) anchor to slice edges, so they can also match where a slice starts or ends mid-output. Don't rely on them for line boundaries.
- All slices of one tick must finish within `READY_MATCH_DEADLINE_MS`. Past it, matching stops and the app reads `crashed` with an error naming the pattern (`readyWhen /<pattern>/ exceeded its <n>ms match deadline and was stopped`); the process keeps running and can be stopped or restarted as usual.
- Rejected at load: invalid regex syntax (`"readyWhen" is not a valid regular expression (…)`), and a repeated group that contains a repeating quantifier (`"readyWhen" nests a repeating quantifier inside a repeated group ("(a+)+"); this shape is rejected because patterns of it can backtrack exponentially …`). The rule is a conservative syntactic one: it rejects every pattern of that shape, including ones that happen to run in polynomial time. Repeating quantifiers are `*`, `+`, `{n,}` and `{n,m}` with `m >= 2`, lazy or not; `?`, `{n}`, `{0,1}` and `{1,1}` are not. Rejected: `(a+)+`, `(\w+\s?)+$`, `(a{1,5})+`, `(?:x*y)*`. Accepted: `(ab)+`, `(a?)+`, `(a+)b+`, `(a+){0,1}`, `[(a+)+]`.
- The load-time check is a heuristic. It does not catch overlapping alternation under repetition (`(a|a)+$`), adjacent overlapping quantifiers (`.*a.*b.*c`) or backreferences; the slice size and the deadline bound those.

There is **no `stop` command**: code-hub owns the lifecycle and stops an app by killing the tracked process group (SIGTERM, then SIGKILL after a 3s grace period).

## Machine-local registration: `registrations.json` (`<projectsRoot>/.code-hub/registrations.json`)

A JSON object keyed by **app id** — a project's directory basename, or `<project>:<key>` for a worktree (see "Worktree manifest inheritance") — each value the same shape as a `.hub.json` body above (validated with the identical schema — `start` required, `name`/`healthPath`/`readyWhen`/`port`/`routes` optional). Fills in a manifest for a project dir or worktree checkout that has **no** `.hub.json` of its own; a real `.hub.json`, even a broken one, always wins over a registration for the same id. Managed via the `register_app`/`unregister_app` MCP tools below, or by hand-editing the file directly (needed for `routes`, since it isn't expressible in `register_app`'s tool schema).

Robustness, mirroring `.hub.json`/`state.json` conventions: whole-file JSON that fails to parse, or isn't a JSON object, is logged (`console.warn`) and treated as an empty registry — it never hides real `.hub.json` apps. A per-entry validation failure (e.g. missing `start`) surfaces that one app as non-startable with `manifestError`, exactly like a broken `.hub.json` does. A registry entry whose key names no discovered app is logged and skipped — no phantom app. One exception is deliberately silent: a key naming a project with at least one **servable** worktree under `<projectsRoot>/.worktrees/` never warns, since that registration is legitimately consumed by those worktrees (the adopted / out-of-root project case). "Servable" excludes a checkout refused for the reserved `:` (below) — nothing consumes a refused one, so a key whose only worktrees are refused **does** warn as orphaned, on every listing, alongside the refusal warning naming the checkout. If you are hand-editing this file, that pair of warnings is the signal to rename the offending directory rather than to re-add the key.

## App settings: `app-settings.json` (`<projectsRoot>/.code-hub/app-settings.json`)

Per-app settings (`src/appSettings.js`): the default login a **new** share of the app starts with, in every mode; the app's fixed port; the app's fixed port; whether code-hub starts the app at boot; and how it shares the app once a start reaches ready. Managed via `GET`/`PUT`/`DELETE /api/apps/:id/settings` (below), which the UI's per-card **Settings** dialog uses.

- **Shape:** `{ "<id>": { "username"?: string, "password"?: string, "autoStart"?: true, "autoShare"?: { "mode": "tunnel"|"lan"|"tailscale", "auth": boolean, "tls"?: boolean, "funnelPort"?: 443|8443|10000 }, "port"?: number } }`, keyed by **exact app id**. A worktree (`<project>:<key>`) does **not** inherit its parent project's entry.
- **Per field, independently:**

  | Field | Unset means | Set means |
  |---|---|---|
  | `username` | `hub` | every new share's Basic-Auth username |
  | `password` | a CSPRNG password per share | every new share's password (masked in the UI, `passwordIsDefault: true`) |
  | `autoStart` | off (stored only as `true`) | `appManager.autoStartAll()` starts the app at boot when it isn't already running |
  | `port` | the manifest's `port`, else a free port | the fixed port of every start of the app, overriding the manifest's; an integer `1024`–`65535` |
  | `autoShare` | off | every start of the app (`start`, `restart`, MCP `start_app`, boot auto-start) shares it with these options once readiness settles to `ready`, with the default login above. For the always-on host code-conductor (never started by code-hub): `appManager.autoShareAlwaysOn()` shares it at every code-hub boot, unless it already has a share |

  An entry with none of the five is deleted, never kept. `autoShare` is stored **normalised** by the same validation `POST …/share` uses (`validateShareOptions` in `src/shareOptions.js`): `auth` defaults to `true`, `tls` is kept for `lan` only and defaults to `true`, `funnelPort` is kept for `tailscale` only and defaults to `443`, any other key is dropped. A stored `tailscale` `autoShare` with no `funnelPort` is read — and reported by `GET …/settings` and the listing's `settings.autoShare` — as `funnelPort: 443`; the file itself is not rewritten.
- **Main checkouts only:** `autoStart`, `autoShare` and `port` act on a project's main checkout. Enabling any (`autoStart: true`, a non-null `autoShare`, or a non-null `port`) for a **worktree** is refused with `400` (`auto-start, auto-share and a fixed port apply only to a project's main checkout — '<id>' is a worktree`). The **host code-conductor** (`alwaysOn`) takes `autoShare`; `autoStart: true` or a non-null `port` for it is refused with `400` (`auto-start and a fixed port don't apply to '<id>' — it is the host code-conductor, which is always on (auto-share does apply)`), the whole body included. A refused body writes nothing. Clearing them is always accepted, and a hand-written `autoStart` on the host conductor's entry is ignored (`autoStartAll()` excludes it). Whether an id is a worktree comes from discovery (or the running record of a source-removed app), never from the id's shape. A hand-written toggle or port on a worktree entry is ignored: no auto-start, no auto-share, a free port; a hand-written port on the host conductor's entry is ignored too (code-hub never starts it).
- **Location:** always under `<projectsRoot>/.code-hub/`, never in a project tree.
- **Mode `0600`:** every write goes to a tmp file created `0600`, `chmod 0600`, then renamed over the file — so the file is owner-only even if it pre-existed looser. `state.json`/`registrations.json` are written with the process umask. **Plaintext at rest** — the file mode is the only protection.
- **Read on every call** (no in-memory cache). Writes (`update`/`clear`) are serialised in-process, so concurrent PUTs for different ids don't drop each other's entry.
- **Corrupt file:** invalid JSON is renamed to `app-settings.json.corrupt` (chmodded `0600`, since it may still hold passwords) with a `console.warn` that omits the parse error (its message can quote the file), and treated as empty; valid JSON that isn't an object is warned about and treated as empty.
- **Not auto-deleted** when an app is unregistered or removed; `DELETE …/settings` clears a stale entry.
- **Migration from `share-defaults.json`** (`migrateLegacyFile()`, first thing in `appManager.init()`): `share-defaults.json` present and `app-settings.json` absent → renamed to `app-settings.json` (contents unchanged — its `username`/`password` entries are valid entries here, with both toggles off) and chmodded `0600`. Both present → neither is touched, `app-settings.json` is used, and a `console.warn` names both paths. Otherwise nothing happens. Idempotent.

## Hub settings: `hub-settings.json` (`<projectsRoot>/.code-hub/hub-settings.json`)

Hub-wide settings (`src/hubSettings.js`, filename `HUB_SETTINGS_FILENAME`). Managed via `PUT /api/hub-settings` (below), which the UI's toolbar **Hub settings** dialog uses; the current values ride on every `GET /api/apps` as `hubSettings`.

- **Shape:** `{ "bridgeFallback": boolean }`.

  | Field | Default (file or key absent) | Meaning |
  |---|---|---|
  | `bridgeFallback` | `true` | open each ready app at the container's bridge address through an in-process forwarder (see "`urls`" under the `App` shape) |

- **Invalid file:** unreadable, invalid JSON, not a JSON object, or a non-boolean `bridgeFallback` → a `console.warn` naming the path (never quoting the parse error) and the defaults. The file is left as it is.
- **Read once per path** and cached: a **hand edit takes effect on the next code-hub start**. `PUT /api/hub-settings` updates the cache and applies at once.
- **Writes:** serialised in-process; tmp file → rename, mode `0644` (nothing secret).
- No migration: an absent file means the defaults.

## In-memory registration (process-lifetime only, never persisted)

Same schema/validation as `registrations.json`, but held in a module-level `Map` (`registerInMemory`/`unregisterInMemory` in `src/projects.js`) instead of on disk — it is never read from or written to `registrations.json`. Precedence for a dir with no `.hub.json`: in-memory wins over a disk registry entry for the same id; a real `.hub.json` still wins over either. Apps sourced this way carry `source: "memory"`. Not exposed via `register_app`/`unregister_app` — those tools remain disk-only. Currently used for exactly one purpose: `appManager.init()` registers the host `code-conductor` checkout this way when code-hub runs embedded (see `docs/architecture.md`), since the conductor carries no `.hub.json` of its own.

## Worktree manifest inheritance

For a project on code-conductor's **local system** — the only kind code-hub scans — cc nests every worktree at `<projectsRoot>/.worktrees/<project>/<key>` (its `LOCAL_WORKTREES_DIRNAME`), whatever directory the project's own tree lives in. (A project on a registered remote system gets a different root — that system's configured `worktreesDir`, else a `.worktrees` beside the project's tree — which never lands under the scanned root.) The intermediate directory name **is** the parent project by construction, so parenthood is read straight off it: nothing about `<key>` is inspected, and **no `<projectsRoot>/<project>` directory is required** — an adopted / out-of-root project's worktrees still surface (nested under the project's own card when the conductor overlay below supplies one, else under a header-only "no main checkout" card). Such a worktree is resolved with the same precedence as any other dir — its own `.hub.json`, then its own in-memory registration, then its own disk registration — all keyed by its app id, `<project>:<key>`. Only when none of those exist for the worktree itself does it fall back to its **parent** project's manifest, resolved with that same precedence (parent's `.hub.json` → parent's in-memory registration → parent's disk registration), inheriting the parent's `source`. This is what lets worktrees of an in-memory-registered project (e.g. the host `code-conductor` when code-hub runs embedded, see `docs/architecture.md`) surface at all, since such a project has no `.hub.json` for git to carry into the worktree checkout. The parent resolves by **name**, against its directory and both registries, so an out-of-root parent can still donate a manifest via a registration. That directory is `<projectsRoot>/<project>` unless the conductor overlay (below) knows the project's real tree and the root scan produced no directory of that name — in which case it is the recorded tree, so an out-of-root parent's own `.hub.json` donates too, not just a registration. If the parent itself has no manifest source, or its own manifest source is broken, the worktree is not inherited into and is skipped entirely — a broken parent manifest never surfaces as an error on the worktree, and never fails discovery. A worktree's **own** broken manifest/registration does surface, as a non-startable app still carrying `isWorktree: true` and its `project`.

**`port` is always stripped from a worktree entry** (`manifest.port` reads `null`), whatever its source. A fixed port is per-checkout, so this applies to both routes by which a worktree could acquire one: the parent-manifest fallback above, and the far more common case of git carrying the parent's tracked `.hub.json` — fixed port included — into the worktree checkout. Enforced once in `discoverApps()`, so every consumer sees a worktree as dynamically-ported without having to re-check.

## Conductor project overlay (embedded only)

Surfaces the projects code-conductor knows about that code-hub's own filesystem scan cannot see — their tree is outside `PROJECTS_ROOT`, or nested under a dot-directory the root scan skips (`.plugins/<name>` is the common case). They become ordinary main-checkout cards at their real path; a project's worktrees under `<projectsRoot>/.worktrees/` then nest under that card as a consequence, which is what stops them rendering under a header-only "no main checkout" card. Worktrees are **not** a precondition for the card.

**Trigger:** `CONDUCTOR_PLUGIN_ID` + `CONDUCTOR_URL` both set (the same "embedded" test `src/hostConductor.js` owns). Standalone code-hub never makes this call and its listing is exactly the filesystem scan's answer.

**Call:** `GET ${CONDUCTOR_URL}/api/projects`, the conductor's own listing — a bare JSON array of `{ name, path, system, ... }`. Fired at `appManager.init()` (awaited once, off the request path) and lazily by discovery once 5s have passed since the last **attempt** — success or failure alike, which is what holds a down conductor to one call per 5s however often the listing is loaded; never awaited on a request. 2s timeout per call.

**What it contributes:** a `name -> absolute tree directory` map (`src/conductorProjects.js`). `discoverApps()` uses it for exactly two things, both additive:

1. A **third pass** emitting a main-checkout row (`isWorktree: false`, `path` = the recorded tree) for a project that (a) the root scan produced **no directory of that name** for, (b) whose recorded path still stats as a directory, and (c) **has a manifest source** there — a `.hub.json`, or a `registrations.json`/in-memory entry keyed by the project name. Condition (c) is the same bar the root pass applies to a directory under the root: no `.hub.json` and no registration ⇒ no card. A manifest source that is present but **broken** counts, and surfaces as a non-startable row carrying its `manifestError`, exactly as in-root.
2. The directory a project **name** resolves to for manifest resolution, so such a project's own `.hub.json` is read at its real tree — both for its own row and for its worktrees' inheritance (see above).

**Precedence:** the filesystem scan wins. A name the root scan produced a directory for is served from that directory, in discovery and in `appDir()` alike, and the overlay row is dropped. That drop gets a `console.warn` naming both paths when it cost a card — the conductor records a **different** directory that still exists and **has a manifest source**, so code-hub could have served it. Either the card on screen describes a checkout the conductor does not mean by that name (wrong path, wrong git info, and any worktrees nesting under it), or there is no card at all where there would have been one. Silent when the conductor's tree has vanished or has no manifest source, since nothing servable was lost — the same scoping the `:` refusals use. Behaviour is unchanged in every case; the warning exists because the disagreement is otherwise silent.

**Rows dropped**, all silently:

- `system` isn't `local` — a project on a registered remote system: its tree *and* its worktrees are on another machine, so neither is under the scanned root and code-hub can serve neither.
- `name` empty, dot-leading, not a single path segment, or carrying the reserved `:` — code-hub's own id rules refuse such a name anyway (a dot-prefixed or `:`-bearing `<project>` under `.worktrees/` is skipped or refused), so the drop costs nothing that was ever visible.
- `path` empty or not absolute — what the conductor emits for a row whose project record it could not parse. It is telling code-hub it does not know where that tree is, so there is no directory to serve and nothing to say; any worktrees of that project stay listed under the "no main checkout" card, which is the honest rendering of exactly that.

**Degradation:** every failure — not embedded, connection refused, conductor restarted on another port, timeout, non-2xx, non-JSON, not an array — is silent and **keeps the last good answer**, so no failure can empty the listing. A *successful* answer always replaces it, including an empty array or one whose every row is refused: that is the conductor saying it knows of no project here, which is an answer. With no successful fetch the overlay is empty and discovery is exactly the filesystem answer.

**`register_app` on a conductor-known id.** `appDir()` and the overlay pass place a project through one predicate (`overlayAppDir()` in `src/projects.js`) over the same snapshot, so they resolve a name to the same directory wherever the root scan's verdict is the same for both. It is not for a root entry that is a **symlink** to a directory: the root scan reads `Dirent.isDirectory()` (false for a symlink) and emits the overlay row at the conductor's tree, while `appDir()` stats the path, follows the link, and answers `<projectsRoot>/<name>`. Whether a symlinked root entry should be served at all predates this overlay, which only makes both answers visible at once. They deliberately differ on condition (c), and that is the one case where a resolvable id has no card: a project with no manifest source shows nothing, yet `register_app` accepts it. It must — `register_app` exists to make a project servable *without* a `.hub.json`, so the id has to resolve before the registration exists. The asymmetry closes itself for as long as the overlay knows the project: registering supplies the manifest source, and the card appears on the next listing. Should the conductor later stop listing it — a successful catalog that no longer names it always replaces the snapshot — a project with no worktrees under the root has nothing left to consume the entry, and the orphaned-registry-key warning starts firing; `unregister_app` is the answer then. Refused, with the ordinary `'<id>' is not an existing directory under the projects root` and nothing written: an id in no snapshot (conductor unreachable, project unknown, or on a remote system) and one whose recorded tree no longer exists.

## HTTP API (`/api`, JSON)

| Method + path | Body | Response |
|---|---|---|
| `GET /api/health` | — | `{ ok: true }` — cheap liveness probe, independent of `appManager` |
| `GET /api/apps` | — | `{ cloudflaredAvailable, tailscaleAvailable, funnelPorts: [{ port, holder }], hubSettings: { bridgeFallback }, apps: [App] }` (`hubSettings`: see "Hub settings" above; `funnelPorts`: every Funnel port — `443`, `8443`, `10000`, in that order — and the id of the app whose tailscale share holds it, a share still coming up included, or `null` when free; a funnel that died on its own reads as free. Only code-hub's own shares count: a port served outside code-hub reads as free) |
| `POST /api/apps/:id/start` | — | running record (`409` already running, or the app has a fixed port (its Settings `port`, else its manifest's) that is already in use — it never falls back to a free one) |
| `POST /api/apps/:id/stop` | — | `{ id, status: "stopped" }` |
| `POST /api/apps/:id/restart` | — | running record |
| `POST /api/apps/:id/share` | `{ mode?: "tunnel"\|"lan"\|"tailscale", auth?: boolean, tls?: boolean, funnelPort?: 443\|8443\|10000 }` (default `"tunnel"`, `auth` default `true`; `tls` LAN-only, default `true` = on; `funnelPort` tailscale-only, default `443`) | `{ kind, url, urls?, funnelPort?, auth, tls?, proxyPort?, fixedPortFallback?, fixedPortHolder?, relay?, containerInternal?, authUrl?, username?, password?, passwordIsDefault?, qrSvg }` (`proxyPort`/`fixedPortFallback`/`fixedPortHolder`/`relay`/`containerInternal` LAN mode only; `funnelPort` tailscale mode only — otherwise a `tailscale` share's response has the same shape as a `tunnel` share's; read its proxy port from `GET /api/apps`'s `tunnel.proxyPort`) (`400` bad mode/`auth`/`tls` type, a `funnelPort` that isn't one of `443`, `8443`, `10000` (checked in every mode, kept only for tailscale), or `auth:false` with `mode:"tunnel"` or `mode:"tailscale"`; `409` not running, the requested Funnel port is already held by another app's tailscale share, a share of the same running app is already in flight (one share operation per app at a time: while one is in flight, another share of the same running app is refused, not queued (`'<id>' already has a share starting — wait for it to finish before sharing again`), whereas a share after a restart waits for the old process's in-flight share, which can no longer commit, instead of being refused), or the app was stopped/restarted — or unshared (`the share of '<id>' was cancelled by an unshare while it was starting` — an auto-share cancelled this way records no `autoShareError`) — while its share was still coming up, in any mode (that share is abandoned: its proxy closed and its tunnel/funnel child killed); `501` `tunnel` mode when cloudflared absent, or `tailscale` mode when tailscale is unavailable; `500` a tailscale share whose funnel tailscale refused, e.g. a Funnel port served outside code-hub — the message carries tailscale's first output line) |
| `PATCH /api/apps/:id/share/credentials` | `{ username?, password? }` (at least one) | `{ id, username, password, passwordIsDefault, qrSvg }`. Edits the live share only and never writes `app-settings.json`; any other body key is ignored. A `password` edit sets `passwordIsDefault: false`. (`qrSvg` regenerated — a cache hit, since the token-URL QR is stable across a creds edit; `400` bad/missing body or the active share has `auth:false`; `409` no active share.) |
| `PATCH /api/apps/:id/share/auth` | `{ enabled: boolean }` | `{ id, auth, qrSvg }` (`qrSvg` tracks the gate — token URL when enabling, plain URL when disabling; `400` non-boolean `enabled`, or the active share is `mode:"tunnel"` or `mode:"tailscale"` — both are always gated; `409` no active share) |
| `DELETE /api/apps/:id/share` | — | `{ id, tunnel: null }` |
| `GET /api/apps/:id/settings` | — | `{ id, username: string\|null, hasPassword: boolean, autoStart: boolean, autoShare: { mode, auth, tls? }\|null, port: number\|null }` — **never the password** (`404` unknown app) |
| `PUT /api/apps/:id/settings` | `{ username?, password?, autoStart?, autoShare?, port? }`, at least one — per field: absent = keep. `username`/`password`: `null` = clear, non-empty string = set (trimmed). `autoStart`: boolean (`false` clears). `autoShare`: `null` = clear, else `{ mode, auth?, tls? }`. `port`: `null` = clear, else an integer `1024`–`65535` | the `GET` shape after the update (`400` body not an object, none of the five keys, an empty/whitespace/non-string login field, a non-boolean `autoStart`, a `port` that is not `null` or an integer in range, an `autoShare` that isn't an object or `null` or that `POST …/share` would refuse (same message), or a toggle or port enabled for a worktree, or `autoStart: true` or a port for the host code-conductor — nothing is written; `404` unknown app). Clearing every field deletes the entry |
| `DELETE /api/apps/:id/settings` | — | `{ id, username: null, hasPassword: false, autoStart: false, autoShare: null, port: null }` — idempotent, and **never `404`s**, so an entry for a removed app can still be cleared |
| `GET /api/apps/:id/settled` | — | `{ id, settled: boolean }`, a **long-poll**: answers once the app's latest start transition is over — readiness settled (`ready` or `crashed`), plus the auto-share that follows it when ticked; for the always-on host code-conductor, its boot auto-share; a start tracked while waiting (a restart) is waited for too — `settled: true`; or at the server cap (`SETTLE_WAIT_MS` in `src/autoRun.js`) with `settled: false`. With nothing in flight (stopped, adopted, settled) it answers at once with `settled: true`. Never `404`s. The UI opens at most one per transition and reloads the listing once when it answers |
| `PUT /api/hub-settings` | `{ bridgeFallback: boolean }` — exactly that key | `{ bridgeFallback }` after the update, applied to every app's forwarder at once (`400` body not an object, any other key, or a non-boolean `bridgeFallback` — nothing is written) |

`id` is the app id: a main checkout's directory basename, or `<project>:<key>` for a worktree (composed by `worktreeId()` in `src/projects.js`, the only place it is built). Worktree keys are scoped per project by code-conductor, so the `<project>:` qualifier is what keeps two projects' same-named worktrees distinct. **`:` is reserved**, which is what makes the id injective. Any directory name feeding an id is refused if it contains one: a root directory (else `a:b` and worktree `a/b` claim the same id) and a worktree's `<project>` or `<key>` (else `.worktrees/a/b:c` and `.worktrees/a:b/c` both claim `a:b:c`). code-hub **enforces this over its own id namespace** rather than assuming code-conductor keeps `:` out of a project name or key: such a directory is not served, and the refusal is logged (`console.warn`, naming the directory) whenever it cost something servable and silent when it cost nothing. `register_app` likewise rejects a `:`-bearing id that matches no worktree, naming the reservation rather than claiming the directory doesn't exist. The id is **opaque** — never split back apart — and always a single path segment: `:` is a legal `pchar`, so `/api/apps/:id/*` matches it either encoded or raw. The UI sends it `encodeURIComponent`'d (`:` → `%3A`), which is the right practice for an opaque id and what the tests exercise.

`start`/`restart` answer with the persisted `store.apps[id]` record, `{ id, project, path, isWorktree, branch, pid, pgid, port, fixedPort, startedSha, startedAt, tunnel }`, plus the app's live `urls` (see the `App` shape; never persisted). `fixedPort` is the effective fixed port at start — the app's Settings `port`, else the manifest's (`null` for a dynamically-ported app and for every worktree); `port` is what the app actually bound, and for a fixed-port app the two are always equal — a fixed port never moves. `restart` needs no special handling: it is stop-then-start, so a fixed-port app lands back on the same port by construction.

**Shares are token/cookie protected by default, in any mode, with a Basic-Auth fallback.** `share` stands up a local reverse proxy (fresh free port). Opening the share URL exchanges a one-time `?__hubauth=<token>` query param for an httpOnly `hub_auth` session cookie (302 redirect, token stripped from the redirected URL); subsequent requests forward on that cookie. HTTP Basic Auth remains available for curl/API clients that can't retain cookies, using the app's default share login (`app-settings.json`, above) where set — each field independently — else username `hub` + a CSPRNG password generated per share. The token and cookie secret are always CSPRNG-generated per share. Either path forwards authenticated HTTP **and WebSocket upgrades** (cookie or Basic only — no token handling on upgrades) to `http://localhost:<appPort>`.
- `mode: "tunnel"` (default): the proxy binds loopback-only and cloudflared points at it, publishing `https://<sub>.trycloudflare.com`. `501` if `cloudflared` isn't installed. `auth` cannot be `false` for this mode (`400`).
- `mode: "tailscale"`: the proxy binds loopback-only and a **Tailscale Funnel** points at it on the public port `funnelPort` (`443`, `8443` or `10000`; default `443`), publishing the node's MagicDNS name — `https://<machine>.<tailnet>.ts.net` on 443, `https://<machine>.<tailnet>.ts.net:<funnelPort>` on the others. The URL is **derived** from `tailscale status --json` (`Self.DNSName`, trailing dot stripped), never scraped from CLI output, and is re-read on every share — so a node rename produces a correct new URL rather than a stale one. Unlike cloudflared's per-launch random hostname it is stable across restarts, though not immutable: a node that re-registers under a taken name gets a numeric suffix and a new URL (see the README's limitations). `tailscaled` terminates TLS on-machine and forwards plain HTTP to the proxy, so this hop is `tls:false` like `tunnel`. Always gated — `auth` cannot be `false` (`400`). **One per Funnel port:** each port holds one tailscale share; a share on a port another app holds is refused `409` with `'<holder>' already has a tailscale share on Funnel port <n> — unshare it, or share on another port`. Re-sharing the app that holds a port replaces its own share normally, on that port or another (which frees the old one). Shares on different ports run side by side. A port served outside code-hub (the user's own `tailscale serve`/`funnel`) or not allowed by the tailnet is refused by tailscale itself: the share fails with `tailscale funnel exited (code=1) before the funnel came up: <tailscale's first output line>` (e.g. `listener already exists for port 8443`), and leaves no proxy and no claim behind. `501` when tailscale is unavailable (`tailscale status --json` doesn't report `BackendState: "Running"` with a non-empty `Self.DNSName`). The funnel runs as a **foreground** `tailscale funnel --https=<funnelPort>` child whose pid is persisted (`state.json`'s tailscale `tunnel` is `{ kind, url, pid, proxyPort, auth: true, funnelPort }`); teardown is SIGTERM to that process, which removes that funnel's config and only it — so a tailscale share, like every other, does not survive a code-hub restart.
- `mode: "lan"`: the proxy binds `0.0.0.0` instead — no cloudflared involved. **Fixed-port apps:** when the app declares a `port`, code-hub first tries to bind the proxy on that same port across the machine's specific LAN IPv4 addresses, so the LAN share URL carries the app's own port. Whether that works depends on how the app itself binds, which code-hub cannot know (it injects only `$PORT`), so it attempts the bind and reads the result rather than guessing: an app bound **loopback-only** leaves the LAN addresses free and the share lands on the fixed port (`fixedPortFallback: false`); an app bound to **all interfaces** (`0.0.0.0`, what a plain `app.listen(PORT)` does) already holds that port on every address, the bind fails with `EADDRINUSE`, and the gated share **falls back to a free port** with `fixedPortFallback: true` and a logged warning.

  An `EADDRINUSE` alone does not say *who* holds the port, and the two possible causes mean opposite things, so code-hub establishes the cause rather than assuming it and reports it as `fixedPortHolder`:
  - `"app"` — the port is held by a bind covering **every** address, which is *almost certainly* the app's own: `start` proved the port free on all addresses before spawning, so the app was its first holder and anything arriving later could only take addresses the app left free. That premise is established at spawn time, though, and this is a share-time conclusion — `share` only knows the start command's wrapper process is alive, not that the app's own listener is still up, so a reloader restarting the server briefly frees the port machine-wide and something else could take the wildcard in that window. Treated as a loud exposure warning, phrased as near-certainty rather than fact.
  - `"other"` — the port is *not* wildcard-held, so an unrelated process holds a LAN address at it and the app is **not** LAN-reachable there. This is the only value that licenses staying quiet, because it is the only one backed by a positive measurement.
  - `"unknown"` — the cause probe could not establish anything. This is **not** an all-clear and is surfaced as a conditional exposure warning: the probe binds a loopback alias, and only Linux configures the whole `127.0.0.0/8`, so on macOS and Windows it fails for *every* port and this is the value they always get. Failing safe here is deliberate — staying silent would hide a genuine ungated exposure, which is the worse direction to be wrong in.

  `fixedPortHolder` is `null` whenever `fixedPortFallback` is `false`. Note that none of these values is an exact attribution: a squatter and the app are indistinguishable at the socket level, and code-hub deliberately does no process inspection. In the fixed-port case the proxy is deliberately **not** bound on loopback, which is why the loopback URL is dropped from `urls`: `<scheme>://localhost:<fixedPort>` would reach the app directly, ungated. `url` is the machine's first non-loopback LAN IPv4 URL (falls back to a `localhost` URL if the host has no LAN interface); `urls` lists every LAN IPv4 URL found (secondary devices can try an alternate if the primary is unreachable, e.g. a Docker bridge address). **TLS is on by default** (`tls` defaults to `true`, overridable per share): the proxy serves HTTPS with a per-share self-signed cert (SAN covers the LAN IPv4s + `127.0.0.1`/`localhost`; generated in memory only), URLs are `https://`, and the session cookie is marked `Secure`. Browsers show a one-time self-signed warning. `tls: false` serves plain HTTP (`http://`, no `Secure` cookie), and the token/cookie/Basic-Auth then cross the LAN in cleartext. Passing `auth: false` drops the gate entirely: no token/cookie/Basic-Auth is generated or checked, every request and WebSocket upgrade forwards unconditionally, and the response has no `authUrl`/`username`/`password` (`url` itself is the whole share link).

Response fields: `kind` (`"tunnel"`, `"lan"` or `"tailscale"`), `url` (primary shareable URL), `urls` (LAN mode only — all candidate URLs), `funnelPort` (tailscale mode only — the Funnel port the share runs on), `auth` (whether the share is gated), `tls` (LAN mode — whether the proxy serves HTTPS; scheme of `url`/`urls` follows it; a `tailscale` share is always `tls:false` on the proxy hop for the same reason a `tunnel` share is — tailscaled terminates TLS on-machine and forwards plain HTTP), `proxyPort` (LAN mode only in this response — the port the gated proxy actually bound; equals the app's fixed `port` unless it had to fall back. A `tunnel` or `tailscale` share does not return it: its proxy is always a fresh free port on loopback, and `GET /api/apps` reports it as `tunnel.proxyPort` for every kind), `fixedPortFallback` (LAN mode — `true` when a fixed-port app's gated share could not take that port, see above), `fixedPortHolder` (LAN mode — `"app" | "other" | "unknown"` naming the established cause of that fallback, `null` when there was none; only `"app"` asserts the app is reachable ungated on the LAN), `authUrl` = the share URL plus `?__hubauth=<token>` (**the QR encodes this** for scan-to-auth when `auth` is true; opening it sets the session cookie and redirects to the credential-free URL — no credentials ever appear in the URL or QR) — omitted when `auth` is `false`, `username`/`password` (Basic-Auth fallback for curl/API clients) — also omitted when `auth` is `false`, `passwordIsDefault` (gated shares — `true` when the proxy was seeded with the app's stored default password and no share-time password edit has changed it since; the UI masks the password on this flag, `password` itself is always the real value), `qrSvg` (of `authUrl` when gated, else of the plain `url`). Credentials live in the server process for the share's lifetime — **never written to `state.json` or logged** — so `GET /api/apps`'s `tunnel.password` re-reveals them across a UI reload; the same call also re-serves `tunnel.authUrl` (rebuilt from the live proxy token) and `tunnel.qrSvg` (a per-app cached render, regenerated only on share/creds-edit/auth-toggle — not on every listing), so the QR and the Open magic-link survive a full UI refresh that wipes the client's in-memory share response. `PATCH .../share/credentials` edits the creds in place on the live proxy (no new URL/token). Torn down on `unshare`/`stop`/`restart`/`start` (starting an app whose process died tears down any share it still had — the URL dies with it). A share does **not** survive a code-hub restart, in any mode: on startup any orphaned share record is cleared (its in-process proxy is gone) and the app needs re-sharing — the next share always starts again from the app's default login if one is set (else `hub` + a fresh auto-generated password), even if the previous one was edited. A LAN TLS toggle re-shares, so it too returns to the default login. Changing the stored default while a share is live leaves that share's password as it is (and still `passwordIsDefault: true`) until the next share.

**LAN share through the host relay** (code-hub in a bridge-networked container; `docs/host-relay.md`). In a container (`/.dockerenv` or `/run/.containerenv`), every LAN share is also exposed through the host relay (scope `lan`, its proxy port) whenever a relay session is up — at share time or later — with no configuration. The response and `tunnel` carry:

- `relay` (`RelayInfo`): `null` when code-hub isn't in a container, or no relay is running on the host (no relay file); else `{ state, error, port, requestedPort, portFallback, recovery }`:

  | Situation | `relay` | `url` / `urls` |
  |---|---|---|
  | code-hub is connecting to or retrying the relay (an attempt in flight, or a backoff timer armed — a relay file that couldn't be read included) | `{ state: "down", error: <the last error — a connection or relay-file read error — or null>, port: null, requestedPort: <proxy port>, portFallback: false, recovery: "retrying" }` | the container's own LAN URLs |
  | the relay file's content can't be used (another protocol version, invalid, not a regular small file) — no retry until it changes | `"down"`, `error`: why, `recovery: "relay-file"` | the container's own LAN URLs |
  | session up, the relay has not reported on this port yet | `"down"`, `error: "waiting for the relay to bind the port"`, `recovery: "binding"` | the container's own LAN URLs |
  | session up, port bound on the host | `{ state: "up", error: null, port: <host port>, requestedPort: <proxy port>, portFallback, recovery: null }` | `<scheme>://<advertised host ip>:<relay.port>` per advertised address — the host URLs only |
  | session up, the relay could not bind it | `{ state: "failed", error: <the relay's message>, port: null, …, recovery: null }` — `no_lan_address`, a bind error, or over `maxPorts` | the container's own LAN URLs |

  `portFallback` is `true` when the proxy port was busy on the host and the relay took a free one. A relay problem **never fails the share**. A share made while a session is up waits for the relay's answer about its port (at most `STATUS_WAIT_MS` in `src/hostRelay.js`) before it answers.
- `containerInternal`: `true` when the relay isn't `up` and the share's LAN addresses are a container's bridge addresses only (every LAN IPv4 in `172.16.0.0/12`). The UI then warns and hides the QR.

The TLS cert's SAN covers the relay's advertised addresses; one advertised after the share was made is added in place (new connections get the re-issued cert). Every relay change — the session coming up or dropping, the port bound, the addresses changing — re-points `tunnel.url`/`urls`/`relay` (and so the QR) and persists; `GET /api/apps` reflects it within seconds. Unshare, stop, restart, a replacing start and an abandoned share all withdraw the port from the relay at once.

`PATCH .../share/auth` flips the gate on a **LAN** share in place — same proxy, port, token, username/password; a tunnel or tailscale share rejects this with `400` (always gated). The underlying proxy's password/token/cookie-secret always exist regardless of the share's initial `auth` value — the token and cookie secret are generated, the password is seeded from the app's default share login or else generated — and are never regenerated on a toggle, so the token-bearing `authUrl` stays valid across an off→on round-trip. The **QR does change with the gate**: the response returns a regenerated `qrSvg` — the token URL when enabling, the plain URL when disabling — so a QR shown for a no-auth share isn't left stale (and 401-ing) once the gate turns on. `GET /api/apps`'s `tunnel.auth`/`tunnel.username`/`tunnel.password`/`tunnel.authUrl`/`tunnel.qrSvg` reflect the live state immediately after a toggle (no re-share needed).

`urls` (top level) is the list of base URLs, primary first, then `http://<lan ip>:<port>` per LAN IP. The primary is decided in one place (`appUrls()` in `src/appUrls.js`, shared by HTTP and MCP), first match wins:

| Primary | When |
|---|---|
| `http://127.0.0.1:<host port>` | code-hub runs in a container and the app is **mirrored on the Docker host's loopback** by the host relay (the host port may differ from `port` when that was busy on the host) |
| `http://<bridge ip>:<port>` | the **bridge-address fallback** holds for the app (below); the bridge IP is then dropped from the LAN entries that follow, so it is listed once |
| `http://localhost:<port>` | otherwise |

Each `routes[].urls` is those bases with the route `path` appended (`/` keeps the clean base form). Both are derived live on every listing (never persisted) and populated only while the app is running. An app is mirrored once it is `ready` (or adopted and alive), never while `starting`; the always-on host conductor never is. `start`/`restart` answer before readiness, so their `urls` start with `localhost` either way.

**Bridge-address fallback** (`src/bridgeForward.js`). An app gets a plain TCP forwarder — no TLS, no login — bound on the container's bridge IP at the app's own port, forwarding to `127.0.0.1:<port>`, while all of these hold: `hubSettings.bridgeFallback` is on; code-hub runs in a container whose local IPv4s are all in `172.16.0.0/12` (`bridgeIPv4()` in `src/net.js`; the bridge IP is the first of them, and only it is bound, never `0.0.0.0`); the app is not the always-on host conductor; the app is `ready` (or adopted and alive); and no LAN share holds it (below). The forwarder doesn't depend on the host relay: it stays bound while the mirror is up, and only the primary URL moves. The bind's outcome, and the bridge URL it offers — the primary unless a mirror outranks it:

| Bind result | Bridge URL offered | Log (`console.error`) |
|---|---|---|
| listening | `http://<bridge ip>:<port>`, through the forwarder | — |
| `EADDRINUSE` — presumably the app itself holds the address (it bound `0.0.0.0` or the bridge IP); no forwarder | `http://<bridge ip>:<port>`, the app directly | `[bridgeForward] <id>: <ip>:<port> is already taken — presumably by the app itself; showing it directly` |
| any other error; no forwarder | none — the primary is the mirror's or `localhost` | `[bridgeForward] <id>: could not bind <ip>:<port> — <message>; no bridge URL for it` |

A failed bind never fails or delays a start, and is **never retried** while the app's record, port and bridge IP stand; a stop, restart, LAN share/unshare or a setting toggle re-evaluates it.

**A LAN share displaces the forwarder.** From the moment a LAN share of the app starts (before it binds anything) until it ends, the app has no forwarder and no bridge URL: its primary is the mirror URL when one is bound, else `localhost` (the share's own URLs are the reachable ones). The loopback mirror is never displaced. A fixed-port LAN share of a loopback-only app therefore binds `<bridge ip>:<port>` itself, gated. Unsharing, re-sharing as `tunnel`/`tailscale` (whether that re-share succeeds or fails), or a LAN share that fails, is cancelled or is abandoned reopens it. `tunnel` and `tailscale` shares leave it up.

**`alwaysOn`.** When code-hub runs embedded as a code-conductor plugin (`CONDUCTOR_PLUGIN_ID` + `CONDUCTOR_URL` env vars present — see `docs/architecture.md`), the main `code-conductor` checkout is reported `alwaysOn: true, status: "running"` with no real pid to track, and `POST /api/apps/code-conductor/start`, `.../stop`, and `.../restart` all reply `409`. `POST .../share` still works — it targets the port parsed from `CONDUCTOR_URL` — and so does its `autoShare` setting, which shares it at every code-hub boot (`autoStart: true` is a `400`; see "App settings"). The checkout's `path` (and its git info) comes from the `CONDUCTOR_PROJECT_DIR` env var the conductor injects, which **may live outside the scanned `PROJECTS_ROOT`** — so the app surfaces even with a custom conductor root; older conductors that don't inject it fall back to discovering a `code-conductor/` dir under the root. This never applies to `code-conductor:<key>` worktrees (always ordinary apps) or when running standalone — though such a worktree may still surface via manifest inheritance from the parent whenever its worktrees are under the root, **including for an out-of-root checkout** (for a local-system project cc roots worktrees at `<projectsRoot>/.worktrees/` wherever the checkout lives; see "Worktree manifest inheritance").

### Errors

Non-2xx responses are `{ error: string }`. Status codes: `400` (the app cannot start — its manifest source failed to parse or validate, and the reason is the app's `manifestError`; an invalid `share` `mode`/`auth`/`tls`/`funnelPort`; `auth:false` with `mode:"tunnel"` or `mode:"tailscale"`; a credentials-edit body that's empty/non-string, or targets a no-auth share; a settings `PUT` refused as described above; a non-boolean `enabled` on an auth-toggle, or one targeting a `mode:"tunnel"`/`mode:"tailscale"` share), `404` (unknown/not-running app), `409` (already running / a declared fixed port already in use / not running for share / the requested Funnel port is already held by another app's tailscale share / a share of the same running app already in flight / an app stopped, restarted or unshared while its share was coming up, in any mode / no active share for a credentials edit or auth toggle), `501` (`tunnel`-mode share when cloudflared is absent, `tailscale`-mode share when tailscale is unavailable — reported in preference to the tailscale `409` when both apply, since it is the more actionable of the two), `500` (unexpected, or a funnel tailscale refused — see `mode: "tailscale"`). **Exception: `POST /api/mcp`** replies `200` for every well-formed tool call, including tool-level failures — see below.

## Host relay protocol (`relay/protocol.json`)

The contract between code-hub (`src/hostRelay.js`, `src/relaySession.js`, `src/relayStore.js`, all reading it through `src/relayProtocol.js`) and the host relay (`relay/relay.py`). **`relay/protocol.json` is its single source**, read at load by both sides: the version, the rendezvous file names, the MAC labels, every frame type, role, scope and error code, the port range, and every cap and timing (`maxAddresses`, `maxRendezvousBytes`, `maxPorts`, `maxFrameBytes`, `maxPendingHandshakes`, `maxHubHandshakes`, `maxIncomingPerPort`, `maxIncomingTotal`, `nonceBytes`, `minSecretLength`, `handshakeTimeoutMs`, `pingIntervalMs`, `keepaliveTimeoutMs`). Tests fail if a source file restates a frame type, role, scope, MAC label, error code or file name inside a string literal (`tests/python/test_relay.py` for `relay.py`; `tests/relay.test.mjs` V17 for the code-hub relay modules); comments, docstrings, a frame's own key names and Node event names are not scanned. Operator guide: `docs/host-relay.md`.

### Rendezvous files — `<projectsRoot>/.code-hub/<rendezvous.dir>/`

| File (`rendezvous.*`) | Writer | Shape | Rules |
|---|---|---|---|
| `hubFile` (`relay.json`) | code-hub | `{ "protocolVersion", "secret" }` — `secret` base64url of 32 random bytes | On every code-hub boot: dir made and chmod'ed `0700`; file created (tmp + rename, `0600`) when missing or invalid (not an object, or `secret` not a string of at least `minSecretLength`), otherwise left untouched. The relay reads only `secret`, on every handshake, and refuses it with `no_secret` (the message naming the path and the reason) when the file can't be read, isn't a regular file within `maxRendezvousBytes`, isn't UTF-8 or valid JSON, or holds no `secret` string of at least `minSecretLength`. |
| *both* | — | — | Read only when a regular file of at most `maxRendezvousBytes`, opened non-blocking (a FIFO, device or oversize file is unusable: code-hub replaces such a hub file and reports such a relay file; the relay refuses connections with `no_secret` naming why). Each writer creates its tmp file exclusively after removing whatever is at its path, so a planted symlink is never written through. |
| `relayFile` (`host.json`) | the relay | `{ "protocolVersion", "listen": "<ipv4>:<port>", "pid" }` | Written atomically (tmp in the same dir + `os.replace`, `0600`) after the control socket is bound, with the bound port. Removed on a clean exit only while its `pid` is still the relay's. code-hub reads it on every connection attempt: missing → no relay; another `protocolVersion`, or invalid or unusable **content** → an error (naming both versions for a mismatch) and no dial until the file changes; a file that couldn't be *read* (an fs error) is retried with backoff instead (the `relay` table's `retrying` row). |

### Framing and handshake

- Raw TCP to the relay's control listener. Each frame is one UTF-8 JSON object plus `\n`, at most `maxFrameBytes`, with a string `t` (a value of `frames`). **Both sides validate strictly**: exactly the required keys, each of its type; anything else is `bad_frame` and the connection closes.
- Every connection, either role, starts with a handshake. Nonces are `nonceBytes` random bytes, base64url without padding; each side checks the peer's length and alphabet.

| Step | Direction | Frame |
|---|---|---|
| 1 | relay → hub, on accept | `{"t":"hello","v":<protocolVersion>,"nonce":Nr}` |
| 2 | hub → relay | control: `{"t":"auth","v","role":"control","nonce":Nh,"mac"}` · data: the same plus `"session":S,"conn":X` |
| 3 | relay → hub | control: `{"t":"welcome","mac","session":S,"addresses":[ipv4…]}` · data: `{"t":"welcome","mac"}`, after which the relay splices at once |
| 3′ | relay → hub | `{"t":"error","code","message"}`, then close |

- code-hub answers a `hello` of another version by closing, with `the relay at <addr> speaks protocol N, this code-hub speaks M — update the relay/ copy on the host`.
- **MAC** = hex HMAC-SHA256, key = the secret (UTF-8), message = `label + "\n" + role + "\n" + Nr + "\n" + Nh + "\n" + session + "\n" + conn` (`session`/`conn` empty for control); `label` is `macLabels.hub` for the hub's MAC, `macLabels.relay` for the relay's. Both sides compare in constant time. The distinct labels stop a relay reflecting the hub's MAC; each side's fresh nonce defeats replay. The secret itself never crosses the wire.
- **Relay checks, in order**: the hub file's secret (unreadable or invalid → `no_secret`, naming the path), the version (`version_mismatch`), the frame shape (`bad_frame`), the MAC (`auth_failed`); data role only: `session` ≠ the current session → `stale_session`; `conn` not pending in it → `unknown_conn` (a conn is consumed by its first claim).
- **code-hub verifies the relay's MAC before using anything from the welcome**, data bytes included; a mismatch closes with `the relay at <addr> could not prove the secret`.
- **Pre-auth caps (relay)**: at most `maxPendingHandshakes` connections pre-auth at once — one more is cut with no hello; no valid `auth` within `handshakeTimeoutMs` → closed; a line over `maxFrameBytes` → closed. code-hub keeps at most `maxHubHandshakes` (< `maxPendingHandshakes`) handshakes in flight, control and data together, from TCP connect until settled, and queues the rest — so code-hub alone never trips the relay's cap.

### Control session

| Frame | Direction | Meaning |
|---|---|---|
| `{"t":"ports","ports":[{"port":P,"scope":S}…]}` | hub → relay | The **full set** of exposures, sent after the welcome and on every change. `scope` is a value of `scopes`: `lan` = a LAN share's container proxy port, `loopback` = a running app's container port. Each entry has exactly `port` (integer in `port.min`–`port.max`) and `scope`; the `(port, scope)` pair is unique. Any violation is `bad_frame`. |
| `{"t":"status","addresses":[…],"ports":[…]}` | relay → hub | One per `ports` frame, in order, one entry per requested pair, scope echoed: `{"port","scope","hostPort","fallback"}` or `{"port","scope","code","message"}` — `no_lan_address` (lan only), `bind_failed`, or `too_many_ports` for entries beyond `maxPorts`, counted across both scopes in frame order. `addresses` = the advertised LAN addresses. |
| `{"t":"incoming","port":P,"scope":S,"conn":X}` | relay → hub | A client connected to the host listener of `(P, S)`; `X` is pending in this session. |
| `{"t":"ping"}` / `{"t":"pong"}` | both | Each side pings every `pingIntervalMs` and answers a ping with a pong. Any frame resets the peer-silence timer; silence past `keepaliveTimeoutMs` closes the session. |
| `{"t":"error","code","message"}` | relay → hub | Fatal (e.g. `bad_frame`), then close. |

- **Bind hosts are fixed by scope in the relay** (`hosts_for`), never taken from a frame: `lan` binds the advertised addresses only (never `127.0.0.1` unless it is itself advertised — tests only); `loopback` binds `127.0.0.1` only.
- **Reconcile on `ports`**: re-probe the addresses — a change closes and rebinds the lan listeners (a failed probe answers lan entries `no_lan_address`; loopback entries are unaffected); close the listeners of pairs no longer present, with their pending and spliced clients; keep unchanged pairs as they are; bind each new pair at `P` on every host of its scope, on `EADDRINUSE` at a free port with `fallback: true`.
- **One session at a time**: a newly authenticated control session replaces the current one, whose listeners all close first. Exposure therefore lasts exactly as long as one session.

### Data path (on demand)

1. A client connects to the host listener of `(P, S)`. Over `maxIncomingPerPort` pending for that listener, or `maxIncomingTotal` for the session, it is cut at once. Otherwise the relay records `conn X`, arms a `--accept-wait-ms` timer and sends `incoming`. Bytes the client sends meanwhile stay buffered (the relay doesn't consume them) and are delivered first once the client is spliced.
2. code-hub looks up its exposure for `(P, S)` — none (withdrawn meanwhile): it ignores the frame and the relay's timer drops the client — else opens one fresh connection to the control session's dial address and authenticates as `data` with `S` and `X`.
3. The relay consumes `X`, cancels its timer, writes the `welcome` and splices client ↔ data connection. code-hub verifies the welcome, then connects the exposure's target — `lan`: the share's auth proxy; `loopback`: `127.0.0.1:<app port>` in the container — writes any bytes that followed the welcome (the client's first bytes, e.g. a TLS ClientHello) and pipes both ways, half-close preserved. A failed target connect destroys the data connection, and the relay closes the client.
4. Unclaimed after `--accept-wait-ms`, a client is cut. A session close cuts every pending and spliced client.

**No frame carries a host or a target**: the relay's only outbound `connect()` is the packet-less UDP route probe, so it can't be made an open proxy.

## UI serving & headers

Owned by `src/webui.js`; mounted after `/api` (so the API answers first).

- **Every response** — the API's, the UI's, the 404, the 503 and error responses — carries `X-Content-Type-Options: nosniff` and exactly this `Content-Security-Policy` (`CSP` in `src/webui.js`):

  ```
  default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; font-src 'self'; img-src 'self' data:; manifest-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'self'
  ```

  | Directive | Why |
  |---|---|
  | `script-src 'self'` | The bundle, `theme-init.js`, and the host's `/pluginBridge.js` (same origin as the page inside cc). No inline script exists |
  | `style-src 'self' 'unsafe-inline'` | `'self'`: the bundle's CSS and the host's `/pluginTheme.css`. `'unsafe-inline'`: the `<style>` element Radix Dialog's scroll lock injects (the QR dialog). Safe only because nothing emits a `style` attribute or element from content |
  | `font-src 'self'` | The Geist fonts the host sheet names (`/pluginTheme/fonts/…`); without it they are blocked silently |
  | `img-src 'self' data:` | `'self'`: the icon. `data:`: the share QR, an `<img>` of the server's SVG |
  | `manifest-src 'self'` | The PWA manifest; `default-src 'none'` blocks it otherwise |
  | `connect-src 'self'` | The relative `api/…` calls |
  | `base-uri 'none'`, `form-action 'none'` | No `<base>`; no form ever submits natively (the Edit form's submit is handled in script) |
  | `frame-ancestors 'self'` | Framed only by code-conductor's page (same origin) |

- **Static paths** (from `frontend/dist`, `Cache-Control: no-cache`; Vite hashes the bundle names):

  | Path | Content-Type |
  |---|---|
  | `/`, `/index.html` | `text/html` |
  | `/assets/index-<hash>.js` | `application/javascript` |
  | `/assets/index-<hash>.css` | `text/css` |
  | `/theme-init.js` | `application/javascript` |
  | `/manifest.webmanifest` | `application/manifest+json` |
  | `/icon.svg` | `image/svg+xml` |

- **No SPA fallback.** Any other path is `404 text/plain` `Not found` — including `/pluginBridge.js` and `/pluginTheme.css` standalone (inside cc, cc serves those itself, before its proxy).
- **Not built.** While `frontend/dist/index.html` is missing, every non-`/api` path answers `503 text/plain` `UI not built — run npm install`; `/api/*` (and so `healthPath`) stays up. Checked **per request**: a build finished while the backend runs is served at once, no restart. The missing file is logged once at startup (`console.error`).
- **Errors outside the API's JSON convention** (an error Express raises before or after the router, e.g. an undecodable path parameter): `text/plain`, status `err.status ?? err.statusCode` when it is 400–599, else 500. A 500 answers `Internal error` and is logged; any other status answers its standard reason phrase (`Bad Request`, …). The error's message is never sent.

## MCP API (`POST /api/mcp`)

code-hub is a code-conductor plugin (see `conductor.plugin.json` at the repo root) and exposes its app-management operations as MCP tools over one endpoint, reusing the same `appManager` logic as the HTTP API above — no duplicated behavior.

**Request:** `{ tool: string, arguments: object, caller: { sessionId, project } }`. `caller` is accepted but currently unused server-side — `appManager` has no per-project scoping, so `start_app`/`stop_app` are not restricted to the caller's own project.

**Response — status-code contract:**

| Condition | Status | Body |
|---|---|---|
| Malformed JSON body | `400` | `{ error }` |
| Missing/non-string/empty `tool` field | `400` | `{ error }` |
| Well-formed call, tool succeeds | `200` | `{ result: <any> }` |
| Well-formed call, tool fails (unknown tool, bad `arguments`, already-running, not-found, ...) | `200` | `{ error: string }` |

The split is deliberate: only a malformed *request envelope* is a transport failure. An unknown tool name, invalid arguments, or a tool throwing (e.g. "already running") are normal MCP outcomes for the calling LLM, so they stay `200` — the conductor can treat any non-200 as a hard transport error without special-casing tool-level failures.

**Tools** (declared in `conductor.plugin.json`'s `mcp.tools`, shallow JSON-Schema `inputSchema`s — no `$ref`/`oneOf`/`anyOf`/nested objects):

| Tool | Arguments | Result |
|---|---|---|
| `list_apps` | none | same as `GET /api/apps` |
| `start_app` | `{ id: string }` | same as `POST /api/apps/:id/start` |
| `stop_app` | `{ id: string }` | same as `POST /api/apps/:id/stop` |
| `register_app` | `{ id: string, start: string, name?, healthPath?, readyWhen?, port? }` | the registered app, in the same shape as an entry in `list_apps`'s `apps` (`source: "registry"`). `400` if `id` isn't an existing dir under the projects root, `409` if that dir already has a `.hub.json`, `400` on a schema violation (e.g. empty `start`, or a `port` outside `1024`–`65535`). An app's Settings `port` overrides the registration's. `routes` isn't in this tool's declared schema (array-of-object properties aren't expressible in the shallow-JSON-Schema `pluginApi` v1 constraint) but is still accepted/validated if passed in `arguments` — the schema simply doesn't advertise it; hand-edit `registrations.json` for multi-route registrations. |
| `unregister_app` | `{ id: string }` | `{ id, registered: false }`. `404` if `id` has no registry entry. No effect on a project with its own `.hub.json` (it was never in the registry). |
