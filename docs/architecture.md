# Architecture

Node + Express backend, vanilla ES-module frontend, no build step. `"type": "module"`, Node 22. Dependencies: `express`, `qrcode`.

## Modules (one responsibility each)

| File | Responsibility |
|---|---|
| `server.js` | Bootstrap: build Express app, mount `/api` + `express.static('public')`, `listenWithRetry` (EADDRINUSE poll), run startup reconciliation once. Port `PORT` (7000), host `HOST` (127.0.0.1). |
| `src/projects.js` | Discovery, in **three passes**. `projectsRoot()` = `PROJECTS_ROOT` ?? parent-of-repo. Root pass: every non-dot directory under the root is its own app (`id === project === basename`). Worktree pass: `listWorktreeDirs()` enumerates `<root>/.worktrees/<project>/<key>` — code-conductor's `LOCAL_WORKTREES_DIRNAME` layout. For a project on cc's **local system** (the only kind code-hub scans) that root is always `<projectsRoot>/.worktrees`, whatever directory the project's own tree lives in; cc picks a different root for a project on a registered remote system (that system's configured `worktreesDir`, else a `.worktrees` beside the project's tree), which never lands under the scanned root. So the intermediate dir name **is** the parent project; nothing about `<key>` is inspected and no `<root>/<project>` sibling is required (that is what keeps an adopted / out-of-root project's worktrees discoverable). `worktreeId(project, key)` = `` `${project}:${key}` `` is the only place a worktree id is composed. `:` is code-hub's **reserved id qualifier**, which is what makes `worktreeId()` injective and the two passes' namespaces disjoint. Every directory name feeding an id is refused if it contains one — a root directory (else `a:b` collides with worktree `a/b`'s id) and a worktree's `<project>` or `<key>` (else `a/b:c` and `a:b/c` both compose `a:b:c`, two checkouts under one id with readdir order deciding which one every action reaches). This is a rule code-hub **enforces over its own id namespace**: it does not assume code-conductor keeps `:` out of a project name or key, it refuses to serve a directory carrying one and degrades loudly — a `console.warn` naming the offender whenever the refusal cost something servable (the dir had its own manifest source, valid **or** broken — a broken `registrations.json` entry with no `.hub.json` counts — or, for a worktree, a parent manifest it would have inherited), and silence when nothing was lost, so an unrelated `:`-named directory can't log on every 2s poll. `WORKTREE_ID_QUALIFIER` is the single definition, read by `appManager`'s `registerApp` for its rejection message. Dot-prefixed `<project>` dirs and any non-directory entry (a symlink included — a `Dirent` for one reports `isDirectory() === false`) are skipped under the worktrees root; `appDir(id)` is the reverse, in three steps: the main dir under the root, else where the conductor records the project (below), else the enumerated worktree whose composed id matches — it never parses an id. A worktree with no manifest source of its own (no `.hub.json`, no own registration, both keyed by its app id) inherits its parent project's manifest and `source` instead of being hidden — needed for worktrees of an in-memory-registered project such as the embedded host `code-conductor` (see below); the parent resolves by **name**, so an out-of-root parent can still donate a registration. A worktree's own broken manifest surfaces as an error row still carrying `isWorktree: true` and its `project`, since parenthood is known before resolution. Reads + validates the manifest (`validateManifestObject`, shared by `parseManifest` and both overlays below). Owns `registrations.json` (machine-local registry, read/write) and overlays it onto a dir lacking `.hub.json`. Also owns a process-lifetime-only `Map` (`registerInMemory`/`unregisterInMemory`, never read from or written to `registrations.json`) overlaid the same way, winning over a disk registry entry on id collision. Tags each app `source: 'manifest' \| 'registry' \| 'memory'` — never null, since a project with no manifest source is not listed at all. The manifest carries an optional fixed `port` (integer `1024`–`65535`, validated in `validateManifestObject`, `null` when absent); `discoverApps()` **strips it from every worktree entry** (`{ ...manifest, port: null }`), which is the single place worktree exclusion is enforced — it covers both the parent-manifest fallback and the git-carried copy of the parent's `.hub.json`. The strip **copies** rather than mutates, since `resolve()` memoizes one manifest object per dir name and the parent's own entry shares it. Conductor overlay pass (third): reads `src/conductorProjects.js`'s snapshot and emits a main-checkout row for a conductor-known local project the root scan produced no directory for, whose recorded tree stats as a directory **and has a manifest source there** (see "Conductor project overlay" below). That last condition is the root pass's own bar: no `.hub.json` and no registration ⇒ no card, in-root or overlay. Worktrees are irrelevant to the decision; they merely nest under the resulting card. `dirFor(name)` is the single name→directory map (root directory if the scan produced one, else the overlay's recorded tree, else `<root>/<name>`), used by `resolve()` so a project's own row and its worktrees' inheritance can never disagree. `overlayAppDir(name, …)` is the single definition of the **location** question — "where does this conductor-known project live" (no root directory of that name wins it, and the recorded path must stat as a directory) — decided through one function by the overlay pass and `appDir(id)` alike, so the two place a project identically wherever the root scan's verdict is the same for both — which excludes a **symlinked** root entry, whose `Dirent` reads `isDirectory() === false` for the scan while `appDir()`'s `fs.stat` follows it (see "Conductor project overlay" below). The manifest-source condition sits in the overlay pass alone, so `appDir()` still resolves an id whose project shows no card; that asymmetry is deliberate and is what lets `register_app` create the missing source. |
| `src/conductorProjects.js` | The host conductor's project catalog, as an overlay: fetch, cache, degrade. `snapshot()` → `Map<name, absoluteDir>` — synchronous, never throws, never blocks, fires a lazy `refresh()` when `OVERLAY_TTL_MS` (5s) has passed since the last **attempt** (success or failure) and none is in flight. `refresh()` → `GET $CONDUCTOR_URL/api/projects` behind `AbortSignal.timeout(FETCH_TIMEOUT_MS)` (2s, which bounds body consumption too), single-flight, never rejects; awaited exactly once, by `appManager.init()`. The single enforcement point for every timeout, row validation and failure-containment decision — `projects.js` only ever sees a plain `Map`. `_setFetchImpl`/`_setClock`/`_reset` are test seams. |
| `src/state.js` | Persists running-apps to `<projectsRoot>/.code-hub/state.json` (atomic tmp→rename). `reconcile()` probes each pid (`kill -0`): adopts live, drops dead, clears dead tunnels. It returns `{ state, strandedTunnels }` — the tunnel records of dropped apps whose OWN share child is still alive. The record is the only place that pid is written down, so deleting it silently would strand the child forever; `state.js` can't kill it (it must not depend on the integrations to learn a share's kind), so it hands it back for `appManager.init` to kill. Corrupt state file is moved aside. |
| `src/net.js` | Free-port allocation, `isPortFree(port)` availability probe, `probeWildcardHold(port)` holder-shape probe, URL enumeration (`enumerateUrls` = loopback + non-internal IPv4 base URLs; `routeUrls` = those bases with a route path appended), TCP readiness probe. `isPortFree(port)` answers "is this fixed port free?" by attempting a **`0.0.0.0`** bind — the strictest probe available, since on Linux `SO_REUSEADDR` does not permit overlapping listen binds, so a wildcard bind fails when the port is held on *any* single address (a listener on `127.0.0.1:P` alone makes `0.0.0.0:P` `EADDRINUSE`). It resolves `false` rather than throwing, and carries the same TOCTOU caveat as `allocatePort` — `appManager.start`'s post-spawn check is the real backstop. `probeWildcardHold(port)` answers the different question "is this port held by a bind covering *every* address?", returning `'held' | 'free' | 'inconclusive'`. It binds the loopback alias `127.0.0.2`, which a wildcard bind covers but which is a distinct address from `127.0.0.1`: `EADDRINUSE` ⇒ a wildcard holder, a successful bind ⇒ any holder is address-specific, any other error (e.g. `EADDRNOTAVAIL` where the alias isn't usable) ⇒ nothing established. Both decisive answers rest on one biconditional — the alias bind must fail `EADDRINUSE` **iff** a wildcard holder exists — so the `CODEHUB_WILDCARD_PROBE_ADDR` test override is validated as a **specific IPv4 address**: IPv4 (an IPv4 wildcard bind can't cover another family), not in `0.0.0.0/8`, and not `127.0.0.1`. Anything else is ignored with a logged warning naming the reason. All three rejections were measured against a port held only on `127.0.0.1`, i.e. with no wildcard holder at all:

  | rejected alias | result | failure |
  |---|---|---|
  | `::1`, `localhost` | binds ⇒ `'free'` | under-report — silent on a real exposure |
  | `0.0.0.0` | `EADDRINUSE` ⇒ `'held'` | over-report — it *is* the wildcard, so it collides with a holder on any single address |
  | `127.0.0.1` | `EADDRINUSE` ⇒ `'held'` | over-report — it is exactly what a loopback-only app binds, so it collides with the app being probed |

  The last two both pass a bare `net.isIPv4()` check, which is why the validated property is the address *class*, not a list of literals. The rest of the IPv4 space is safe: unconfigured addresses (`0.0.0.0/8`, `192.0.2.1`) only ever yield `EADDRNOTAVAIL` ⇒ the fail-safe `'inconclusive'`, and broadcast/multicast literals were measured to satisfy the biconditional, so they are left alone. The fallback is to the default rather than to `'inconclusive'`, so a bad value can't make the probe go permanently dark either. Tri-state on purpose, so `share()` can report "unknown" instead of asserting a cause it hasn't proved. `localIPv4s({ lanFallback })` is the single source of truth for the machine's non-internal IPv4s — used by both `enumerateUrls` and the LAN-TLS cert's SAN (`appManager` → `selfsigned`). `enumerateUrls(port, { lanFallback, scheme })` takes a `scheme` (default `'http'`; the LAN-share path passes `'https'` when TLS-wrapped). `enumerateUrls(port, { lanFallback })` defaults `lanFallback` to `false`: plain enumeration only reports what `os.networkInterfaces()` natively sees. Only the LAN-share path (`appManager.js`'s `share(id, { mode: 'lan' })`) passes `lanFallback: true`, so that — and only that — call, when `os.networkInterfaces()` finds no non-internal IPv4 (observed on Termux/Android, which sandboxes netlink-based interface enumeration for unprivileged apps even though the LAN address is still visible to ioctl-based tools), falls back to shelling out to `ip -4 addr` then `ifconfig -a` and parsing the output (`parseLanIPv4s`, exported for tests), excluding loopback and point-to-point (`/32`) VPN-tunnel addresses; briefly cached so repeated share calls don't repeatedly spawn a subprocess. |
| `src/git.js` | `headSha` / `currentBranch` / `lastCommitAt` (`git log -1 --format=%cI`) via `execFile` (manual promisify — Termux Node lacks `promisify.custom` on `execFile`). |
| `src/runner.js` | Process lifecycle. Spawns `bash -lc <start>` **detached** (own group, pgid === pid) with `PORT`. Readiness orchestration, per-app 16KB output ring for crash tails, `stop` = SIGTERM→SIGKILL on the process group. If the child dies almost immediately with `EADDRINUSE` (the allocated port got claimed before bind), retries on a freshly allocated port, up to 3 times, before surfacing a crash. `start(app, port, { fixed })` — with `fixed: true` (a manifest `port`) that retry is **skipped entirely**: reallocating would silently defeat the pin, so the `EADDRINUSE` surfaces as a crash on the requested port, which `appManager.start` turns into a `409`. The returned `port` is then always the requested one. `fixed` defaults to `false`, so dynamic-port callers and the two existing retry tests are untouched. |
| `src/tunnel.js` | cloudflared detection (`--version`, bin from `CODEHUB_CLOUDFLARED_BIN`) + quick-tunnel spawn, capturing the `*.trycloudflare.com` URL (30s timeout). Now targets the **auth proxy** port, not the app port. |
| `src/tailscale.js` | Tailscale Funnel integration; a separate module from `tunnel.js` because it shares none of its mechanics (bin from `CODEHUB_TAILSCALE_BIN`). `available()` reads `tailscale status --json --peers=false` (`--peers=false` keeps the payload bounded — `list()` calls this on every poll) and requires `BackendState: "Running"` **and** a non-empty `Self.DNSName`; it deliberately does NOT check `Self.CapMap` for the funnel capability, whose key is version-unstable. The URL is **derived** from `Self.DNSName` (trailing dot stripped), never scraped from CLI output — so a wording change in tailscale's banner can only cost a readiness timeout with a clear message, never a wrong URL. `startFunnel(port)` spawns `funnel --bg=false --yes http://localhost:<port>` detached; readiness is the **derived host appearing in the child's output**, which is why output is still read at all: it is self-validating (tailscaled agrees with our derivation) and it catches a tailnet that refuses Funnel — that only surfaces as a nonzero exit, and resolving straight after spawn would hand back a URL that never answers. 15s backstop. `stopFunnel(pid)` = SIGTERM to the process **group** — the group, not just the leader, which `tests/tailscale.test.mjs` pins via a fixture that spawns a child of its own. `waitForExit(pid)` polls until the child is actually gone, SIGKILLing the group after 5s: the CLI reverts the node's WHOLE serve config as it exits, so a replacement funnel spawned while an older one is still shutting down can have its URL revoked moments later. It polls rather than awaiting an exit event because after a code-hub restart the child is ours only by pid. **Why foreground:** it needs no off-command at all. `tailscale funnel reset` would clear the user's unrelated `serve` config, and a targeted `off` isn't in 1.102.3's `--help`; a foreground CLI owns its funnel config for its own lifetime and removes it on exit. That makes "SIGTERM removes the funnel config" a contract with someone else's binary — measured by hand on 1.102.3 before this was written, and held afterwards by the `RUN_REAL_TAILSCALE=1` smoke test. |
| `src/authproxy.js` | In-process HTTP reverse proxy. Per-request auth resolves `?__hubauth=<token>` (query, sets an httpOnly `hub_auth` cookie + 302-redirects with the token stripped) → `hub_auth` cookie → HTTP Basic Auth (`hub` + per-share CSPRNG password, curl/API fallback) → 401. WS upgrades accept cookie or Basic only (no token handling — the cookie rides along automatically), forwarding via raw `net` socket pipe (`req.rawHeaders` replayed) to `localhost:<appPort>`. `startAuthProxy(targetPort, { host = '127.0.0.1', port = 0, auth = true, tls = null })` → `{ port, hosts, auth, username, password, token, setCredentials(), setAuth(), close() }` (the cookie secret is never returned). `port` defaults to `0` (a fresh free port) or pins a specific one; `host` takes a string **or an array of addresses**, each getting its own `http`/`https` server sharing the one `handler`, credentials, token and `sockets` set — one proxy identity, N listeners. The port from the first bind is reused for the rest, so every address serves the **same** port; a failed bind closes the servers already bound (never leaking a partial bind) and rejects with Node's error, whose `code: 'EADDRINUSE'` is what the fixed-port LAN share branches on. `close()` closes every server. This is what makes a same-port LAN share possible at all: a proxy can bind `<lanIp>:<P>` alongside an app on `127.0.0.1:<P>`, but not alongside one on `0.0.0.0:<P>`. `tls: { key, cert }` (LAN shares only) makes it serve **HTTPS** via `https.createServer` instead of plain HTTP, and marks the session cookie `Secure`; the WS-upgrade + raw-socket-upstream path is identical either way. Tunnel- and tailscale-mode shares never pass `tls` (cloudflared, off-machine, and `tailscaled`, on this machine, each terminate TLS upstream and forward plain HTTP to this hop, where a `Secure` cookie would be dropped — same reasoning, two causes). Password/token/cookie-secret are **always** CSPRNG-generated, regardless of the initial `auth` value — `auth: false` (LAN shares only) skips only the gate itself: no token/cookie/Basic checked, every request/upgrade forwards unconditionally, and `username`/`password` read as `null` (hidden, not absent) while ungated. `username`/`password` are mutable in place via `setCredentials({ username, password })` — computed live per-request, so an edit takes effect on the next request with no server restart. `setAuth(enabled)` flips the gate itself in place (backs `appManager.setShareAuth`, LAN only) — since secrets are never regenerated, the port/token/cookie-secret/creds stay identical across any number of toggles, so a token URL (and its QR) issued while gated keeps working after the gate turns off; a plain URL/QR issued while ungated does NOT work after re-gating (no token → 401) — which is why `setShareAuth` regenerates the QR on toggle; an existing session cookie, being independent of username/password, also keeps working through a credentials edit. Loopback-only by default; hand-rolled (no proxy dep). |
| `src/selfsigned.js` | `generateSelfSigned({ ipAddresses, dnsNames, validityDays })` → `{ key, cert }` PEM. Builds a self-signed X.509 v3 cert (RSA-2048, sha256, SAN from the given IPs/DNS) with `node:crypto` only — no openssl (not on the target device) and no dependency (keeps deps at express+qrcode). Used by `appManager` to TLS-wrap LAN shares; the cert is generated per share and kept in memory only. |
| `src/qr.js` | `qrcode` → inline SVG string (async). |
| `src/appManager.js` | **Single source of truth.** Composes discovery ∪ running-state; exposes `init/list/start/stop/restart/share/unshare/registerApp/unregisterApp`; keeps `state.js` in sync. Holds the in-memory `proxies` map + `teardownShare`, which dispatches teardown via `killShareChild` on `rec.tunnel.kind` (`'tailscale'` → `tailscale.stopFunnel`, else `tunnel.stopTunnel`) and stays **synchronous**, so the in-memory maps are consistent the instant it returns. The SIGTERM it sends is NOT awaited, though: for tailscale that lingering exit would revert the node's serve config, so the pid is recorded in `expiringFunnelPid` and the next tailscale share waits it out with `waitForExit`. `killShareChild` is split out for the one case with no record left to tear down — a pid handed back by `reconcile` — and takes `{ verify }`, set only on the two `init()` paths that signal a pid read off disk rather than one this process spawned: `tailscale.looksLikeFunnel(pid)` checks `/proc/<pid>/cmdline` first, because a persisted pid can have been recycled while code-hub was down and this path SIGTERMs (then SIGKILLs) a whole process **group**. It answers true where it cannot tell (no `/proc`), since never reaping a real orphan leaves a PUBLIC URL up — the worse outcome, and the reason the sweep exists. **The invariant: no path drops or replaces a record carrying a live share pid without first killing that pid** — the record holds the only copy of it. Every such site therefore goes through `teardownShare`, and that is what makes the slot below reliable rather than a fourth thing to keep in sync: `init`'s handling of `reconcile`'s `strandedTunnels` and its orphan sweep; `list()`'s app-died-unnoticed branch, which tears down before `delete store.apps[id]` (reachable for an ADOPTED record, which can hold a live tunnel with no runner runtime, so the crashed/exited branch above it doesn't claim it); `list()`'s reap of a tailscale funnel whose own pid has died; `stop()`; `unshare()`; and `start()`, which is reached only once the app's pid is dead but overwrites the record wholesale with `tunnel: null` — its share child can still be alive. **The Funnel slot** (`funnelSlot`, `{ id, pid, pending }`) is the single authority for which app holds the node's Funnel, and the only input to the `409`; nothing scans the records for a holder. It is a **reservation**, not a derived view: `share()` claims it synchronously before its first await, because `rec.tunnel` isn't written until the funnel is up (up to the readiness backstop), so two concurrent requests would otherwise both pass any records-based check, both spawn, and leave one app advertising a dead public URL with live credentials. A `pending` claim blocks its **own** app too — a second concurrent share of A would orphan the first's proxy and funnel child. It is released precisely when the child it *names* is killed (`killShareChild` matches on pid, never on id: `share()` claims the slot and then tears down that same app's previous funnel, so an id-keyed release would drop the claim it just made), plus by `reapFunnelSlot()` when the named funnel has died on its own. On failure `share()` hands the slot back to the previous holder if that funnel is still alive — a refusal thrown *before* teardown leaves the old share fully intact, and freeing the slot there would let another app raise a competing funnel in front of it — and frees it otherwise. `share(id, { mode, auth, tls })` dispatches three ways. For `mode:'tailscale'` it resolves the blocker from `funnelSlot` synchronously; when blocked it still awaits `tailscale.available()` first and reports **`501` in preference to `409`** (with both true, "tailscale isn't available" is the more actionable message, and no claim is made on that path so the await races nothing). Unblocked, it claims the slot, checks `available()` (`501`), tears down any existing share, waits out `expiringFunnelPid`, then starts a loopback-only auth proxy with no `tls` and points `tailscale.startFunnel` at it, closing the proxy if the funnel fails to come up. Before writing its result it **re-validates that `store.apps[id]` is still the record it started with**: a `pending` slot carries no pid, so `killShareChild`'s pid match cannot protect an in-flight share, and `stop()`, `list()`'s prune and `start()` are all free to drop the record during the seconds the funnel takes to come up. Writing on regardless would attach a LIVE public funnel to a detached object — reachable by no `unshare`/`stop`, never persisted, and never reaped (it is alive), so it would `409` every future share on every app until a restart, which would then lose the last reference to it. On divergence it kills the funnel, closes the proxy and throws `409`. A `committed` flag marks the point past which the funnel is up and recorded: after it, a failing `persist()`/QR render must not run the hand-back, because the slot already names reality. For `mode:'lan'`, `tls` defaults to `true` when omitted and, when on, generates a per-share self-signed cert (`selfsigned`, SAN from `localIPv4s` + loopback), passes it to `startAuthProxy`, and emits `https://` URLs; `rec.tunnel.tls`/`list()` carry the flag. `start(id)` reads the manifest's fixed `port` (already `null` for worktrees) and, when set, guards it twice: a **pre-check** (an existing running record on that port, naming the holder, then `isPortFree`) for a clean refusal in the ordinary case, and a **post-spawn check** (`runner.runtime(id)` crashed with `EADDRINUSE`) that closes the TOCTOU window between probe and the child's own bind and also catches a child that failed for a reason the probe can't see. Either fires a `409` and leaves nothing running — the two together are what make "a fixed port never silently moves" true rather than merely likely. The declared port is persisted as `fixedPort` on the running record so `share()` can read it without re-running discovery. `registerApp`/`unregisterApp` write/delete entries in `projects.js`'s `registrations.json`, following the same guard-then-mutate-then-persist shape as `start`/`stop`. |
| `src/routes.js` | Thin Express router over `appManager` + `mcp`. |
| `src/mcp.js` | Dispatches `POST /api/mcp` tool calls (`list_apps`/`start_app`/`stop_app`/`register_app`/`unregister_app`) by name to `appManager`; always resolves — never throws — so the route replies `200` with `{result}`/`{error}` for any well-formed call; see `docs/protocol.md`. |
| `src/hostConductor.js` | Detects plugin-embedding (`CONDUCTOR_PLUGIN_ID` + `CONDUCTOR_URL` env vars) and identifies the host code-conductor checkout by id, so `appManager` can treat it as always-on. `hostConductorDir()` returns the conductor's injected checkout dir (`CONDUCTOR_PROJECT_DIR`, may be outside the projects root; null when unset/not embedded); `hostConductorPort()` parses the port from `CONDUCTOR_URL`. |
| `public/` | `index.html`, `styles.css`, `app.js` (`el()` helper, 2s poll, flat client-side sort, per-app hue accent bar, relative "edited" labels, **client-side worktree grouping** into expandable subcards), `manifest.webmanifest`, `icon.svg`. All local asset refs and API calls are **relative** (no leading `/`) so the same files work standalone at `/` and mounted under a code-conductor plugin prefix. The 2s poll (`refresh({ periodic: true })`) skips its `render()` call while any credential edit is open (`state.credEdit` non-empty) so it can't tear down/refocus the edit's `<input>`s mid-keystroke — same "suppress re-render churn while in flight" idea as the `busy` set, just gating the periodic tick instead of a button; any manual action (Save/Cancel/Unshare/Stop/Restart) still re-renders immediately. |

## Process & state lifecycle

- **App identity** = the app id: a main checkout's directory basename, or `<project>:<key>` for a worktree (`worktreeId()`). It is opaque — never split apart — and never used as a filename or hostname; the one id→dir resolution outside discovery is `registerApp`'s `appDir(id)`. A running record holds `{ id, project, path, isWorktree, branch, pid, pgid, port, fixedPort, urls, startedSha, startedAt, tunnel }`. `fixedPort` is the manifest's declared `port` (`null` when dynamic, and always `null` for a worktree); it is persisted so `share()` can see it without re-running discovery, and so it survives restart adoption. For a fixed-port app `port === fixedPort` always — the port never moves.
- **Own process group**: children are spawned `detached`, so the child is its group leader and `pgid === pid`. Stop kills the whole group via `process.kill(-pgid, sig)` — this works even after the source dir is gone, because only the pgid is needed.
- **State outside project dirs**: state lives in code-hub's own `.code-hub/` at the projects root, so a running server survives (and remains stoppable) even if its source/worktree is deleted; such an app is flagged `sourceMissing`.
- **Startup reconciliation** (`appManager.init` → `state.reconcile`): live pids are **adopted** (shown `running`; we can't recapture their stdout, so no in-memory runtime — readiness is assumed), dead pids dropped, dead tunnels cleared. Detached children intentionally outlive a code-hub restart. A share child whose APP pid died in the same window needs explicit handling: `reconcile` drops that record before `init`'s orphan sweep can read it, so it returns those `strandedTunnels` and `init` kills them first (see `src/state.js`). (A backgrounded `funnel --bg` would be worse still — it has no pid at all, so nothing could ever record that a funnel exists. That is part of why the foreground model was chosen.)
- **Readiness / status**: for apps started this process, `runner.runtime(id)` supplies `starting`/`ready`/`crashed`; adopted apps have no runtime and read as `running`. `list()` lazily prunes records whose pid has since died. A port race (`EADDRINUSE`) that persists past `runner.js`'s retry budget still ends up `crashed`, same as any other launch failure. A **fixed-port** start never retries at all: it refuses up front (`409`) when the port is already taken, and refuses again if the child still hits `EADDRINUSE` after a clean probe — no record is persisted either way, so a refused fixed-port start leaves the app `stopped`, never running on some other port.
- **Out-of-date**: `outOfDate = startedSha && currentSha && startedSha !== currentSha`, computed live per `list()`.
- **Routes & last-edited**: `list()` also computes, per app, `lastCommitAt` (source dir's last commit date) and `routes` — the manifest's `routes` (or a single implicit `/` when absent), each with `urls` enumerated live from the running port via `routeUrls`. The top-level `urls` stays the base-URL list persisted at start.
- **Share auth lifecycle**: `share(id, { mode, auth })` starts an `authproxy` (in-memory handle in the `proxies` map, keyed by app id; password/token/cookie-secret held only there, never persisted), points cloudflared at the proxy port (tunnel mode only — always gated, `auth:false` is rejected), and persists `tunnel = { kind, url, urls, pid, proxyPort, auth, fixedPortFallback }` — deliberately **no username/password** in the persisted record. `kind: 'tailscale'` persists `{ kind, url, pid, proxyPort, auth: true }`: always gated, never `tls`, and `pid` is the foreground `tailscale funnel` child that owns the funnel config. For a **fixed-port** LAN share it first attempts `startAuthProxy(rec.port, { host: lanIps, port: rec.fixedPort })` — binding the specific LAN addresses rather than the wildcard, which is the only arrangement that can coexist with the app's own bind. Achievability is decided by *attempting* the bind, never by guessing how the child bound: success means the LAN share serves the app's own port (`fixedPortFallback: false`); an `EADDRINUSE` logs a warning and falls back to the ordinary `0.0.0.0` free-port proxy with `fixedPortFallback: true`, which `list()` and both share responses surface so the UI can warn.

  That `EADDRINUSE` has two possible causes that mean **opposite** things, so the cause is established rather than assumed and reported as `fixedPortHolder`: `probeWildcardHold(fixedPort)` distinguishes a wildcard holder (`'app'`) from an address-specific one (`'other'` — an unrelated process holds a LAN address, and the app is *not* LAN-reachable there), falling back to `'unknown'` when the probe establishes nothing.

  `'app'` is a strong inference, **not** a proof: `start()` proved the port free on every address before spawning, so the app was its first holder and any later arrival could only take addresses the app didn't. But that premise is spawn-time and the conclusion is share-time — `share()` gates on `state.pidAlive(rec.pid)`, and `rec.pid` is the `bash -lc` wrapper, not the app's listener, so under `start: "npm start"` with a reloader the wrapper outlives a server restart. In that window the port is free machine-wide and something else could take the wildcard. Exact attribution is impossible anyway — a squatter and the app are indistinguishable at the socket level — and code-hub deliberately does no process inspection (`ss`/`lsof`/`/proc`), so the messages are phrased as near-certainty instead.

  `'other'` is the only value backed by a positive measurement and so the only one that may stay quiet. **`'unknown'` must warn**: the probe binds a loopback alias, and only Linux configures the whole `127.0.0.0/8`, so on macOS and Windows it returns inconclusive for *every* port — treating that as an all-clear would silently drop the warning for an app that genuinely is answering ungated on the LAN. Both error directions are pinned: over-reporting (blaming the app for a squatter) invites the user to treat the gate as pointless, and under-reporting hides a real exposure. Any non-`EADDRINUSE` error still propagates. Dropping the loopback entry from the LAN `urls` becomes load-bearing here: in the fixed-port case the proxy isn't bound on loopback at all, so `<scheme>://localhost:<fixedPort>` would reach the app **directly, ungated**. Tunnel shares are unchanged (loopback, `port: 0`), which never collides with the app's fixed port. `list()` reads `username`/`password` back from the live `proxies` map (not from `tunnel`) whenever a share is active, which is how the password survives a UI reload without ever touching `state.json`: the proxy handle already outlives a reload (only a full code-hub restart clears it, at which point `tunnel` is cleared too, so there's nothing stale to read). `updateShareCredentials(id, { username, password })` looks up the same live proxy and calls its `setCredentials()` in place — no new proxy, no new URL/token — then returns a `qrSvg` (a cache hit — the token-URL QR is stable across a creds edit, since the token/URL/proxy are untouched); the client folds it back into its share state on the same shape as the auth-toggle response. `setShareAuth(id, enabled)` similarly looks up the live proxy, rejects (`400`) unless `rec.tunnel.kind === 'lan'` (a tunnel share is always gated), else calls `proxy.setAuth(enabled)`, persists the new `rec.tunnel.auth`, and returns a regenerated `qrSvg` tracking the gate — the token URL when enabling, the plain `url` when disabling — so a QR shown while ungated isn't left stale (and 401-ing) once the gate turns on; the client folds it into its share state (same `mergeShareCreds` wiring as a credentials edit). `list()`'s existing `tunnel.auth`/`username`/`password` derivation needs no changes to reflect the flip, since it already reads live off the proxy's getters each call. `list()` additionally rebuilds `tunnel.authUrl` (via `withToken` on the live proxy `token`) and serves `tunnel.qrSvg` from a per-app in-memory `qrCache` (regenerated only when the QR's inputs — `url`/`authUrl` — change, i.e. on `share`/`updateShareCredentials`/`setShareAuth`, **not** on every poll; cleared in `teardownShare`); `share`/`updateShareCredentials`/`setShareAuth` and `list()` all build the QR through one `cachedQrSvg()` so the value served to every client and returned by every PATCH is identical. This is how the QR and the Open magic-link survive a full UI refresh that wipes the client's in-memory `state.share` — `GET /api/apps` re-serves both, the same way it already re-serves `username`/`password`. `appManager`'s `authUrl` is the share URL plus `?__hubauth=<token>` (via `withToken`) — the browser-clicked "Open" link; opening it exchanges the token for a session cookie inside the proxy, so the shared document's own URL is credential-free. The **QR** encodes that same token URL (via `withToken`) — scanning it exchanges the token for the cookie the same way the Open link does (a no-auth share has no token; its plain `url` is the whole story). `teardownShare` closes the proxy + kills the tunnel on `unshare`/`stop`/`restart`. Because the proxy is in-process it **cannot** survive a code-hub restart, so `appManager.init` (after `state.reconcile`) tears down every persisted tunnel and clears it — the share simply needs recreating (a broken tunnel is never left running, and any custom credentials are gone — the next share always starts with a fresh auto-generated password).
- **Worktree grouping is client-side**: the payload stays a flat `apps` array carrying `project`/`isWorktree`/`branch`; `public/app.js` `render()` nests worktrees under their parent's card (expand state in a `state.expanded` set, re-applied across polls). A worktree whose `project` isn't in the payload gets `orphanParent()`'s header-only "no main checkout" card. For an adopted / out-of-root project — worktrees under the scanned root, checkout not — the conductor overlay normally supplies the real parent row instead, so this card is the **fallback**: standalone code-hub, an unreachable conductor, a project the conductor doesn't know, one whose recorded tree is gone or has no manifest source, or an in-root directory with no manifest source.

## code-conductor plugin integration

- `conductor.plugin.json` (repo root) declares code-hub as a plugin: `backend.start`/`healthPath` (`GET /api/health`, a cheap liveness route independent of `appManager` — see `docs/protocol.md`), `frontend.path`/`navLabel`, and `mcp.endpoint`/`scope`/`tools`.
- `public/index.html` loads `<script src="/pluginBridge.js" defer>` **absolute on purpose** — the conductor serves this script at the top level (not proxied per-plugin), so it must resolve against the origin root regardless of code-hub's mount prefix. Standalone (no conductor), the request 404s from code-hub's own static handler and the page is unaffected — the bridge no-ops outside an iframe.
- Everything else browser-resolved (asset `href`/`src`, the webmanifest's icon `src`, every `fetch()` call in `app.js`) is relative, so the identical `public/` files work both at `http://host:7000/` and proxied under `/plugins/code-hub/`. `server.js`'s `renderIndex()` cache-busting rewrite matches both relative and absolute refs, but only appends `?v=` to files it can actually `stat` under `public/` — `/pluginBridge.js` isn't one, so it's left untouched.
- **Host conductor as an always-on app** (`src/hostConductor.js`, wired into `src/appManager.js`): when embedded, the conductor is already running the code-hub child, so offering Start/Stop for it would spawn a duplicate or kill code-hub's own host. `appManager.init()` synthesizes a `store.apps['code-conductor']` record with no pid/pgid (port parsed from `CONDUCTOR_URL`, always `127.0.0.1:<port>` — conductor and its plugin children share one loopback network by construction, confirmed against the conductor's plugin supervisor design). Two paths locate the checkout dir's `path`:
  - **Injected dir** (modern conductor): `hostConductorDir()` returns `CONDUCTOR_PROJECT_DIR`, used directly as the record's `path` — **always**, regardless of the root scan, so this is never shadowed by anything `discoverApps()` finds. This dir **may live outside the scanned `PROJECTS_ROOT`** (a conductor with a custom root keeps its own checkout elsewhere). `init()` also registers it in-memory (`registerInMemory(HOST_CONDUCTOR_ID, { start: 'npm start', name: 'code-conductor', healthPath: '/' })` — see `src/projects.js`'s in-memory overlay above) when the id resolves to **anything** under the root: this dir, **or** at least one `.worktrees/code-conductor/<key>` checkout. That second arm is load-bearing because a worktree is **not** necessarily a sibling of the checkout it branches from: for any local-system project cc roots worktrees at `<projectsRoot>/.worktrees/<project>/`, so an out-of-root conductor routinely has in-root worktrees. Without it those worktrees would have nothing to inherit and would drop out of the listing. When neither exists the registration is skipped, since it would only do harm — it'd let `discoverApps()` resolve an unrelated same-named dir under the root (if one happens to exist) and shadow the real injected-dir record in `list()`'s merge, or, with no such dir, make `discoverApps()`'s orphaned-registry-key check warn on every call for nothing. When out-of-root (the common custom-root case), `discoverApps()` never returns this id at all — `list()`'s second loop surfaces the `store.apps` record anyway (`manifest: null`), and `build()` special-cases `isHostConductorId` so the out-of-root record is **not** flagged `sourceMissing` (its git info reads from `path`).
  - **Discovery fallback** (older conductor, no `CONDUCTOR_PROJECT_DIR`): the checkout carries no `.hub.json` of its own, so `init()` unconditionally registers it in-memory first (same call as above — this path is always under the root, since discovery is how its `path` gets found at all), then discovers a `code-conductor/` dir under the root (not a worktree) and takes its `path`.

  `list()` reports it `status: "running"`/`alwaysOn: true` unconditionally (skipping the normal pid-liveness branch); `start()`/`stop()`/`restart()` reject it with `409`; `share()` skips its pid-liveness check (the only two fields sharing needs are `port` and `pid`, and there's no real pid to check). **Known assumption:** identification is purely by directory basename (`id === 'code-conductor'`) gated on being embedded — a worktree can never collide (its id always carries a `:<key>` suffix), but renaming the actual `code-conductor` checkout directory would silently defeat the fallback path; the injected-dir path avoids this since it's told the dir explicitly. Standalone code-hub (no `CONDUCTOR_*` env vars) never registers or shows `code-conductor` at all, unless it's separately given a `.hub.json` or a disk registration. A `code-conductor:<key>` worktree with no `.hub.json`/registration of its own inherits the in-memory manifest via `src/projects.js`'s worktree-parent-fallback (see `docs/protocol.md`'s "Worktree manifest inheritance") whenever such a worktree exists under the root, which includes the case of an **out-of-root** checkout — the guard above registers in-memory on exactly that condition — so it surfaces and is independently startable/stoppable like any other worktree.
- **Conductor project overlay** (`src/conductorProjects.js`, read by `src/projects.js`): the root pass sees only directories directly under `PROJECTS_ROOT`, so a project whose tree is outside the root, or nested under a dot-dir the pass skips (`.plugins/<name>` is the common real case — "outside the root" is the wrong test), is invisible to code-hub however servable it is. The conductor knows where every project's tree is, so when embedded code-hub asks it and surfaces those projects as ordinary main-checkout cards. Their worktrees, which cc nests at `<projectsRoot>/.worktrees/<project>/<key>` whatever directory the tree lives in, then group under that card instead of under `orphanParent()`'s header-only one — a consequence of the card existing, never a condition for it.
  - **Precedence, the one rule:** the filesystem scan wins; the overlay only fills gaps. A row is emitted only for a name the root scan produced **no directory** for, whose recorded path stats as a directory, and that has a manifest source there. Standalone, the snapshot is empty and both the overlay pass and `dirFor()` degenerate to the filesystem-only answer by construction, not by a rule anyone maintains. A suppression is warned about only when it cost a card — see `warnRootScanShadowedConductor()`.
  - **The path is stat-verified, never composed from an id.** It comes off the conductor's record; `listWorktreeDirs()` remains the single directory enumerator and the overlay pass enumerates nothing. `overlayAppDir()` is where the location question is answered, for the overlay pass and `appDir()` both, so one project can never be placed in two directories.
  - **Budget:** 2s per call (`AbortSignal.timeout`, so body consumption is bounded too), never awaited on a request path. `snapshot()` fires a refresh when 5s have passed since the **last attempt finished** — success or failure alike (`lastAttemptAt` is stamped in a `finally`), which is what caps a down conductor at one call per 5s instead of one per 2s poll. `appManager.init()` awaits exactly one `refresh()` so the first `GET /api/apps` already has an overlay.
  - **Failure containment:** not embedded ⇒ no fetch ever; refused/timeout/non-2xx/non-JSON/non-array ⇒ keep the last good snapshot and retry after the TTL (never cache "unreachable" — an adopted backend can hold a stale `CONDUCTOR_URL` across a conductor restart); a malformed row ⇒ skip that row, keep the rest. The snapshot is replaced atomically on success and retained on **every** failure, so no failure can empty the listing. A *successful* answer always wins, including an empty array or one whose every row is refused — "the conductor knows of no project here" is an answer, not a failure.
  - **The suppression warning** (`warnRootScanShadowedConductor()`): a root directory of the same name always wins, silently — that is what standalone code-hub does too. It is announced only when it cost a card: the conductor records a **different** directory that still exists and has a manifest source there, so code-hub could have served it, and either the card on screen describes a checkout the conductor does not mean by that name (any worktrees nesting under it included) or there is no card where there would have been one. The counterfactual is resolved against the conductor's directory directly, never through `resolve()`, whose memoized answer for that name is about the ROOT directory. `fs.realpath` on the root directory only, since the conductor's path is already one.
  - **The conductor's own project is the exception to trusting the record:** `CONDUCTOR_PROJECT_DIR` is the checkout the conductor is *running from*, which may be a worktree of itself, while its project record names the main checkout. The snapshot substitutes the injected dir for `HOST_CONDUCTOR_ID` at the single point it is built, so the overlay, `appDir()` and `appManager`'s always-on record cannot disagree.
  - **No card without a manifest source.** The overlay pass emits a row only when `resolve(name)` found a `.hub.json` or a registration at the recorded tree — the same bar the root pass applies in-root. A **broken** source still counts and still surfaces as a non-startable row carrying its `manifestError`; a project with no source at all is simply not listed, and any worktrees of it keep the orphan-parent card.
  - **`appDir()` and the listing disagree in two cases, one of them deliberate.** The deliberate one: a conductor-known project with no manifest source resolves as an id while showing no card. It has to — `register_app` exists to make a project servable *without* a `.hub.json`, so the id must resolve before the registration exists, or the only route left is hand-editing `registrations.json`. The asymmetry closes itself for as long as the overlay knows the project: registering supplies the manifest source, and the card appears on the next poll. Should the conductor later stop listing it — a successful catalog that no longer names it always replaces the snapshot — a project with no worktrees under the root has nothing left to consume the entry, and the orphaned-registry-key warning starts firing; `unregister_app` is the answer then. An id in no snapshot (conductor unreachable, unknown, or remote-system) or whose recorded tree has vanished is refused by both.

    The undeliberate one: a root entry that is a **symlink** to a directory. The root scan reads `Dirent.isDirectory()`, false for a symlink, so the listing considers the name root-scan-absent and emits the overlay row at the conductor's tree; `appDir()`'s root branch stats the path, follows the link, and returns `<root>/<name>` before `overlayAppDir()` is reached. The divergence begins in the root scan, upstream of the shared predicate, so the predicate cannot close it. Whether a symlinked root entry should be servable is a standing question older than the overlay — `listWorktreeDirs()` refuses one under `.worktrees/` for the same `Dirent` reason — and the overlay changed only that both answers are now visible at once.
  - `public/app.js` is **unchanged**: `render()` already treats any `isWorktree: false` row as a main card and groups worktrees by `project`, so an overlay row nests its worktrees with no frontend work — deliberately keeping this off the untested render path.

Measured, a `127.0.0.1` holder and a `0.0.0.0` holder read as busy under a `0.0.0.0` bind, a `127.0.0.1` bind *and* a connect check alike, so neither of those tests can tell the implementations apart; only an address that is neither loopback-proper nor the wildcard separates them, and it does so without needing a LAN interface — so the probe stays guarded on a LAN-less host where the end-to-end LAN tests skip. `probeWildcardHold` is covered the same way: `'held'` for a wildcard holder, `'free'` for a `127.0.0.1`-only holder and for an untouched port, plus the alias-validation guards in both directions — a non-IPv4 override (`::1`, `localhost`, `::`) must never reach `'free'` (only `'free'` licenses staying quiet), and a non-specific one (`0.0.0.0`, `127.0.0.1`) must never reach `'held'` against a port with no wildcard holder (only `'held'` licenses shouting). A third pins that the fallback target itself still reports a genuine wildcard hold, so the validation can't trade one error direction for the other. `public/shareState.js`'s `resolveFixedPortNotice` (the warn-vs-note decision, extracted from `app.js` so it is testable without a DOM) is pinned in `tests/shareState.test.mjs`, including the case that matters most: an `'unknown'` holder still returns `level: 'warn'` while stopping short of asserting the app is exposed. `resolveCredNote` (the panel's "how is this reachable" line) was extracted for the same reason and is pinned in the same file — the panel used to branch on `kind !== 'lan'`, so a tailscale share would have rendered as a cloudflared tunnel; the four LAN arms (auth × tls) are pinned verbatim alongside it. `tests/net.test.mjs` also unit-tests the exported `parseLanIPv4s` text parser against canned `ip -4 addr`, busybox/toybox `ifconfig`, and legacy net-tools `ifconfig` samples (including this project's own captured Termux/Android output), asserting loopback and point-to-point (`/32`) addresses are excluded — kept host/network-independent by never touching the real `child_process`/`os` APIs; it also covers `enumerateUrls`'s `scheme` param and `localIPv4s`. `tests/selfsigned.test.mjs` asserts the generated cert parses (`crypto.X509Certificate`), carries the requested SAN entries, is within its validity window, and actually serves over a real `https.createServer`.
- Fixed-port end-to-end coverage: `tests/runner.test.mjs` reuses the deliberate-blocker pattern with `{ fixed: true }` to pin that the returned port **did not move** and the app is `crashed` with `EADDRINUSE` (the dynamic retry test right above it is the contrast). `tests/routes.test.mjs` drives the HTTP API: a fixed-port app starts on exactly that port and `restart` returns the same one; a worktree of it (requested as `/api/apps/app%3Aab12cd/start`, encoded as the client sends it — also the end-to-end proof that a `:`-bearing id survives the REST surface) starts on a free port instead; and three tests each defeat one guard so the other must carry the case alone — a busy port (pre-check), a port held only on a LAN address where the child would never report `EADDRINUSE` (pre-check only), and a `flaky` child that fails after a clean probe (post-spawn check only, and the case a retrying runner would silently move). LAN-share branches assert `proxyPort === fixedPort` with `fixedPortFallback: false` for the loopback-binding app and the reverse for the `wildcard` one (which must also report `fixedPortHolder: 'app'` — the under-report guard on the exposure warning), with the fallback share still gated (401 without credentials). A third test stands an unrelated HTTP listener on a LAN address at the fixed port *after* the loopback-binding app started — the same `EADDRINUSE`, opposite meaning — and asserts `fixedPortHolder: 'other'`, that the app is genuinely not what answers on the LAN there, and that the share is still gated: the over-report guard. A fourth exercises the **probe-unavailable host class on Linux** by pointing `CODEHUB_WILDCARD_PROBE_ADDR` at `192.0.2.1` (RFC 5737 TEST-NET-1, which is never configured, so the bind fails `EADDRNOTAVAIL` for held and free ports alike — measured to reproduce the macOS/Windows behaviour exactly; the override is validated as an IPv4 literal, and a valid-but-unconfigured one like this is honoured): a genuinely wildcard-binding app must still report `'unknown'` rather than `'other'`, and the test confirms the app really is answering ungated on the LAN. Without it the defect would be invisible, since it cannot occur on the platform CI runs. All four skip when the host has no LAN interface, and the `'app'`-attribution test additionally skips where the loopback alias isn't bindable.
- Real-dependency smoke tests (`tests/smoke.real.test.mjs`) are gated behind an env flag. `RUN_REAL_CLOUDFLARED=1`: a raw quick-tunnel check, plus an end-to-end auth check (real tunnel → auth proxy returns 401 anonymous, 200 credentialed). `RUN_REAL_TAILSCALE=1`: the tailscale twin, split into **two** tests. The first pins that SIGTERM to the foreground funnel actually removes the funnel config — the one assumption the teardown model rests on, and the one thing no fake can prove — and makes NO network request, so it runs wherever tailscale is up. The second is the 401/200 gate check, which additionally needs the node's MagicDNS name to resolve from that host and skips with a reason when it does not (a container on a Docker resolver with tailscaled in userspace-networking mode cannot, though the funnel itself registers fine). They are separate precisely because gating the first behind the second once left the load-bearing contract unverified whenever the network was the broken thing. It asserts on `tailscale funnel status --json`, **never** the text form: while a foreground funnel is live the text prints `# Funnel on:` followed by `No serve config` (the handler lives under the JSON `Foreground` key and never enters the persistent serve config), so a text assertion would pass whether teardown worked or not. It snapshots the node's funnel JSON first, asserts the live funnel visibly changes it, and asserts teardown restores it exactly; `finally`-cleanup keeps a failure from leaving 443 funnelled. This is the one test in the suite that opens **public** state.

## Conventions & future changes

- State-file format changes get a one-shot idempotent migration at startup; application code assumes the current shape only (see the workspace migration guidelines).
- The `.hub.json` schema and the HTTP API have no external consumers — change the schema/API and its callers together rather than shimming old shapes.
- LAN shares serve HTTPS by default (per-share `tls`, on unless turned off from the Edit form); certs are self-signed and per-share, so browsers warn on first visit — an accepted, documented trade-off (no public CA can vouch for a LAN IP). Flipping TLS can't happen in place (scheme/cert are bound at proxy creation), so the UI re-shares on change; if a signed-cert or persistent-CA story is ever needed, `src/selfsigned.js` is the seam.
